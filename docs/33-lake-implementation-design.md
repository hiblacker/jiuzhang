# 入湖系统详细实施设计与验收任务

## 1. 范围与当前证据

本设计承接[主实施方案](31-warehouse-implementation-plan.md)与[真实源发现](32-whole-database-discovery.md)，作为开发和验收依据；哪些能力已经落地以代码、迁移和[实际运行记录](34-lake-implementation-evidence.md)为准。

第一交付目标是指定 MySQL 系统的整库与每日持续入湖，随后完成每日文件、REST API、标准模型、质量、数据集与控制台。当前已发现 157 张基础表、2,228 个字段、3 张无主键表，全部 InnoDB；首批全量计划已在本地生成并已由真实执行器验证。再次执行前复核清单是否变化，覆盖分母以当前固定清单为准，不硬编码为 157。实际批次和剩余边界见[实现与验收记录](34-lake-implementation-evidence.md)。

长期目标保持通用数仓定位。DevOps 状态、团队历史、指标公式不进入平台连接器；无法确认的业务语义不阻塞原始数据接收，但不能发布未经定义的业务指标。

## 2. 代码分工与存储边界

| 位置 | 本次实现职责 | 复用与边界 |
|---|---|---|
| `apps/control-api` | 来源、对象清单、计划、系统批次、资产、计划触发及查询 | 复用来源、任务、身份、审计和批次服务；不在 HTTP 请求中执行整库抽取 |
| `apps/ingestion-worker` | MySQL/目录/API 适配、原始对象写入、校验与完成提交 | 把夹具读取与真实读取拆成明确适配器，保留原测试；复用租约、心跳和 Worker 角色 |
| `migrations` | 清单、系统批次、对象结果、持久化引用与日历账本 | 先核对 V001–V008，扩展现有实体；仅新增顺序迁移，不修改已执行 SQL |
| `apps/console` | 无构建依赖的只读入湖控制台 | 先实现接入必需页面；接口与权限由服务端控制，后续可迁移到统一前端栈 |
| `deploy` | 本地开发运行、持久目录、角色、调度入口及恢复说明 | 使用独立测试资源，不覆盖未知容器、卷、端口或既有服务 |
| `tools`、`tests` | 接入预检、验收与故障注入、合成输入和黄金结果 | 真实源明细与凭证不提交；合成测试结果与真实源验证分别报告 |

源库只读；平台元数据、原始对象、加工结果及消费访问分别控制权限。湖区使用配置的持久化根目录，禁止从 HTTP 接收任意本机路径；目录来源必须在管理员批准的根路径内，防止 `..`、符号链接或路径替换越界。

## 3. 最小对象模型

以下是逻辑契约；实现时映射到现有表和新迁移，不按名称机械地另建重复表。

| 对象 | 主标识与关键字段 | 必须保持的约束 |
|---|---|---|
| 接入计划 | `plan_id`、`source_id`、`plan_version`、方式、时区、启停、超时、限额 | 已用于运行的计划版本不可覆盖；变更生成新版本 |
| 对象清单 | `inventory_id`、源范围、发现时点、Schema 指纹 | 系统批次固定引用一个清单版本 |
| 来源对象 | 清单、对象 ID、名称、类型、列定义、主键、必需标志、支持状态 | 无主键和空表仍在覆盖清单中；不可读对象不能静默跳过 |
| 逻辑运行 | 来源、计划版本、应执行窗口、`run_key` | 定时与手工触发使用同一去重规则；一个窗口不能出现多个未区分修订的成功结果 |
| 系统批次 | 逻辑运行、`batch_id`、attempt、revision、状态、租约、读取边界、快照范围 | 系统完整性取决于必需对象结果；最新完整指针条件更新 |
| 对象结果 | 系统批次、来源对象、状态、实际记录/字节数、Schema、清单引用 | 每个必需对象有结果；零条是合法结果，未读取不是零条 |
| 原始对象 | 不可变对象 ID、内部路径、格式、字节数、行数、哈希、编码与类型版本 | 先持久化再引用；同一对象 ID 不覆盖内容 |
| 来源位置 | 对象、已提交水位、来源游标、接收批次、版本 | 已接收水位与已解析、已加工水位分开，不因加工失败重复推进 |
| 交付账本 | 应有窗口、到达状态、首次/最后观察、迟到、更正、补采关联 | 无交付契约时不推断缺失；缺失历史不能用当前态冒充 |
| 数据集发布 | 契约/模型版本、输入资产、候选结果、质量结果、活动版本 | 加工成功不等于发布；旧运行不能覆盖新发布；查询绑定发布及授权范围 |

外部可读状态和内部状态机要有固定错误码。原始对象可用、解析成功、模型通过、数据集发布分别表达，不能共用一个含混的 `SUCCESS`。

## 4. 状态与提交协议

### 4.1 状态层次

逻辑运行可处于 `PLANNED / RUNNING / COMPLETE / INCOMPLETE / FAILED / CANCELLED`。对象接收进度区分 `DISCOVERED / WAITING_READY / READING / RAW_COMMITTED / FAILED`，解析与加工另记状态。沿用现有等价状态时提供映射，不改变既有 API 含义。

失败后新增 attempt，修订产生 revision；不是将旧成功记录改回运行中。停机后过期租约进入对账，失去租约的 Worker 即使仍在运行也不能提交。

### 4.2 原始对象写入与恢复

1. 以不可复用的 attempt 路径暂存，流式写入并累积字节/行数和哈希。
2. 关闭文件、执行选定存储后端要求的持久化动作，重新核验完整性。
3. 封存不可变对象及清单，在元数据事务中登记引用；仅此后推进接收位置。
4. 所有必需对象完成后提交系统清单，再条件更新最新完整指针。
5. 在文件已封存但元数据未提交等崩溃点执行协调；孤立暂存记录为待清理，不能擅自删用户原件或已引用对象。

文件系统和 PostgreSQL 没有同一事务。必须实际验证磁盘满、文件写入失败、元数据提交失败、进程终止和旧 Worker 提交；单靠单元测试不能证明恢复协议正确。

## 5. MySQL 整库读取

- 首批默认全部 FULL_SNAPSHOT；来源范围固定为用户指定库，凭证只通过本地引用读取。源表和列标识符只来自已核验清单，按数据库规则引用；查询值参数化，不接受任意 SQL。
- 核验 SeaTunnel 现有适配能否表达共享快照、逐表原始输出、类型保真与取消；不足时实现同一 Worker 契约下的受控 JDBC 适配，并记录选择依据，不并行维护两套完整链路。
- 同一时点整库快照须用经过证明的共享一致性读取。独立连接按表读取只能标记为表级快照集合；连接中断后不得把新快照内容拼入旧快照。
- 流式分片，限制并发、超时和磁盘用量；无主键表采用完整读取。空表有 Schema 和零行清单。源库只读，不自动建索引、启用 binlog 或申请扩大权限。
- 数据保真覆盖 Decimal、大整数、Float、日期/时间、文本、NULL、空字符串；先锁定编码契约再写入。复合主键按列序保存；不要将 JavaScript Number 用作全类型无损载体。
- 每表及系统批次保存实际读取时间、快照语义和对账结果。信息模式估计行数只作规划，不作为精确完成校验。
- 从全量转增量必须验证游标、重叠窗口、提交顺序、删除和索引；无可靠条件时继续快照。CDC 仅在完整变更需求及实际权限、日志保留和重建流程验证后启用。

## 6. 每日运行和目录接入

### 6.1 持久化调度

调度器产生计划触发，平台日历账本负责应有窗口与运行结果，Worker 负责执行。只使用一个调度器驱动同一任务；复用既有 DolphinScheduler 路线，当前已通过同一受控入口验证一个本地窗口，尚不把一次运行冒充长期跨日稳定性。

默认按日配置，时区与触发点显式保存；排队、并发、超时、重试、补跑和暂停可配置。服务重启后对比应有窗口发现遗漏，限制积压追赶速度，不能冲击源库。页面关闭不影响运行。

当前态来源无法重建过去缺失快照时，标记缺失，补采记录实际时点；事件源只有覆盖历史且仍可访问时才能按历史窗口补读。

### 6.2 文件交付

目录由外部传输工具填充；平台不绑定 FTP/SFTP。来源声明每日单文件、多文件包、事件式到达或封闭轮转文件，不将一种模式套到全部目录。

按完成清单/完成标记/原子改名识别闭合。若只能检测稳定大小和修改时间，必须显示完整性限制。多文件包以包清单判齐，文件名日期不自动决定唯一批次。

文件身份由来源、逻辑交付、版本和内容哈希共同决定。相同内容可能属于不同业务日，不做全局静默去重。同名新内容形成修订；旧原件保留。缺失、空交付、重复、迟到、更正、半写、断连和无法解析分别记状态。

### 6.3 四类解析

| 格式 | 必需支持与验证 |
|---|---|
| CSV | 编码、分隔符、引号、跨行字段、表头、NULL、日期、小数、前导零、流式限制 |
| Excel | `.xlsx` 工作表/表头/范围、日期系统与公式缓存；不执行宏和公式代码；`.xls` 单独标明是否支持 |
| JSON/JSONL | 对象/数组入口、记录路径、嵌套类型与大文件；数组展开规则显式，不自动制造额外业务行 |
| Parquet | Schema、Decimal、Timestamp、时区、逻辑类型和压缩兼容；多文件 Schema 差异可见 |

先保存原件，再在独立解析步骤生成结构化资产；坏行策略按契约阻断或隔离并记录数量，不悄悄丢弃后报告全量成功。

## 7. API、建模与消费

REST 首版支持固定源地址、认证引用、page/size、offset/limit、token/next-link、时间窗口、最大页数、限流退避和响应契约。分页须有循环检测和终止上界；next-link 不能把凭证带到未批准域名。HTTP 200 不自动等于业务成功。

每个响应片段留存原文与脱敏请求说明，认证头和 Cookie 不入湖。接收成功后提交片段位置，解析位置独立；失败恢复验证重读与幂等。缺真实 API 时可先用标注清楚的本地模拟服务开发并验收通用协议，不能声称真实 API 已接入。

模型先采用 Git 中版本化 SQL 与既有 dbt 组合，明确粒度、唯一键、依赖、输入版本和时间语义。构建候选结果并运行非空、唯一性、关联完整性和已定义业务规则；通过后原子发布。未知状态和不完整历史作为数据限制呈现，不编造映射。

消费端通过受控查询接口或数据集专用只读视图访问，参数化查询、标识符白名单、分页/限额和服务端行列授权不可省略。查询、导出、下钻和缓存关联同一 release 与权限范围；不暴露任意用户 SQL 或直接湖区路径。

## 8. API 契约实现顺序

先检查现有 `/api/v1` 接口，优先复用资源；下表为需要补齐的操作，不要求重复创建一套路径。

| 操作 | 输入与响应要求 | 验证重点 |
|---|---|---|
| 来源连接与目录发现 | 来源引用、指定范围；返回发现任务 ID 和清单版本 | 凭证不返回；只读；认证与 TLS 错误分类 |
| 计划创建/变更 | 对象清单、策略、调度、时区、限额；返回不可变版本 | 无权限拒绝；来源范围不扩张 |
| 运行/重试/取消/补采 | 逻辑窗口、修订原因、幂等键；返回批次及状态 | 重复、并发、过期租约、陈旧任务提交 |
| 覆盖与批次查询 | 来源/批次、分页；返回必需/成功/失败/未覆盖计数 | 计数来自同一固定清单与批次，不能跨版本拼接 |
| 原始资产详情/预览 | 资产 ID、行数上限；返回 Schema、受控预览及来源信息 | 行列权限、敏感字段、资源上限、无路径泄露 |
| 模型构建与数据集发布 | 模型版本、输入资产、候选结果与预期当前 release | 质量失败保旧；版本与授权一致；旧运行拒绝 |

控制台完整显示加载中、空数据、缺失、无变化、不完整、失败、重试中和无权限状态，操作结果必须来自后端，不用静态假状态替代联调。
