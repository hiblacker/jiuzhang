## 1. 如何提供连接信息

使用[不含凭证的模板](templates/devops-db.example.json)。本地填写文件为项目下`secrets/devops-db.local.json`；`secrets/`已被Git忽略，实际文件不提交、不输出到聊天、不附在报告中。

Git忽略不是加密或文件访问控制。应保存在可信本机、限制为操作用户可读并遵循组织终端/备份要求，不上传网盘、工单或聊天。当前仅验证Git忽略，未自动修改或验证Windows ACL。需要更高安全级别时按组织密钥管理方案提供引用，不能声称当前明文模板等于密钥库。

| 配置字段 | 填写要求 |
|---|---|
| engine / server_version | 如MySQL、PostgreSQL、SQL Server、Oracle及已知版本；未知版本可留空，engine必须先明确，不猜默认端口 |
| environment | test / replica / production等实际环境，确认是否生产，优先测试库或只读副本 |
| host / port | 当前工作电脑可访问的主机及端口；不是要求将数据库暴露到公网 |
| database / service_name | 数据库名称；服务名/SID等依引擎补充，不适用项留空；不要把service_name和SID混用 |
| username / password | 专用最小权限只读账号，不用root、sa或管理员账号；非密码认证先说明，不改成明文密码方案 |
| tls | 是否强制加密、校验服务端证书、CA文件路径；默认要求加密与校验，证书问题先解决，不静默关闭验证 |
| network_notes | 本机已连接的VPN/隧道或白名单要求，仅描述，不填写VPN密码；网络访问配置另行确认 |
| access.allowed_schemas | 经授权可查询元数据的schema/库范围；初始空列表表示未指定；本轮用户另已明确允许所有库的元数据发现，需记录该显式授权，不普遍将空列表解释为全部库 |
| access.seed_tables | 已知线索STORY和DEFECT，大小写/schema以实际元数据为准 |
| access.metadata_only / allow_business_row_samples | 初始true/false：只看结构，不读取真实业务行；采样前另行确认字段与范围 |
| limits | 拟使用单并发、连接10秒/语句15秒超时；须由实际驱动/数据库适配落实，不是写进JSON便已生效 |

这是人工交接格式，不是现成组件的配置协议；现有脱敏/无认证预检工具，以及固定缓存Docker客户端的只读发现工具。后者初次严格TLS连接失败，用户明确授权测试调查例外后已成功连接并查询元数据，见[当前发现记录](15-source-metadata-findings.md)。不需要安装新驱动。验证配置仅报告缺失字段名称和脱敏状态，绝不打印密码、完整连接串、原始驱动异常或配置内容。

本地文件用编辑器填写，保持合法JSON；Windows证书路径可使用正斜杠，反斜杠和密码中的引号需按JSON转义。不要通过包含密码的命令行参数、终端历史或截图交接。填写完成后在聊天回复“数据库类型为X，连接文件已填好”，不用再粘贴连接串。

## 2. 权限与执行边界

本次测试库例外：用户明确允许使用已配置账号并查询所有账号可见库，无需另建账号。下列最小权限为正式接入要求；本次工具仍限定只读元数据，不读取业务行、不写入源库。

- 账号由源库管理员创建并实施最小权限。第一阶段只需查看授权范围的表/列/索引/约束/注释等元数据；部分数据库的目录可见性依赖对象权限，按真实引擎设计，不为了看表而给管理员权限。
- 不执行INSERT/UPDATE/DELETE、DDL、存储过程调用、数据修复、全库备份或权限变更；不对源业务库压测。
- 先获取元数据，不执行全库COUNT(*)、SELECT *或历史日志内容全文扫描。元数据查询也分页、限制范围和耗时；超时停止分析原因，不自动放开限制。
- 只读账号及适用的只读会话是实际控制；配置里的metadata_only不是数据库权限的替代品。遇到权限不足，不自动扩大授权。
- 配置与查询结果仅本机处理；公开搜索不得携带内部库名、表结构、数据或连接信息。
- 原始结构快照也可能敏感，默认放被忽略的work/中，不自动提交真实DDL、注释或业务样本。经脱敏与确认的字段映射、结论和合成数据才能入库。

## 3. 查找历史表的流程

### 第一阶段：仅元数据，当前授权范围

1. 确认引擎、版本及可见schema；检查STORY/DEFECT存在性、类型、主键、索引、列、注释与约束。
2. 检查STORY中是否存在区分需求/任务的类型列、父子关系或关联表；未看到证据前不宣称某列就是区分依据。
3. 查找与两表有关的外键、引用列和表注释，并检索HISTORY、AUDIT、ACTION、CHANGE、LOG等候选名称；关键词只是检索线索，不表示已找到真实历史表。
4. 检查候选表是否有对象类型、对象ID、事件ID、字段名、前后值、生效/记录时间等结构。考虑操作主表+字段变更明细表、JSON审计、归档表、无外键关联等可能形式。
5. 输出“已确认结构/候选关联/待验证问题”，区分没有表、账号不可见、历史已归档、日志不含前后值等情况。

### 第二阶段：有限采样，另行确认业务行范围

如仅看结构不能确认关系，先给出拟查询字段、对象ID/时间范围、行数与耗时限制，经用户确认后采样。只查询匿名ID、状态变化及必要时间字段；不读取标题、描述、评论正文或附件。测试记录优先。

验证STORY/DEFECT如何对应历史对象类型、状态代码如何映射、更新日志与业务生效时间是否一致、重开事件如何排序，以及需求与任务/团队关系的有效区间。只有候选表名不算通过，需有结构或受控样本证据。

事件保留年限、删除/归档、日志延迟和团队归属历史仍需核实。“有操作历史”不自动代表所有历史指标可还原。
