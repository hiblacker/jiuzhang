## 0. 需求与结论

用户提出的四件事：**按表接入**、**写 SQL 接入**、**其它成熟接入方式**、**字段重命名**，以及接入后**有页面能查看已入湖数据**。

结论先行：

1. **按表接入基本已具备**，缺的是"逐表策略"与"字段口径"，属增量扩展而不是新建通道类型。
2. **增量（水位）接入是当前最该补的能力**：数据库层已预留 `UPDATED_AT_KEYSET` 策略枚举，但 Worker 只实现全量快照。
3. **"写 SQL 接入"必须改造为"登记式 SQL 定义"**：平台硬约束不允许任意用户 SQL（见 §3.4），因此设计为只读、参数化、版本化、需评审的 SQL 模板，而不是在线 SQL 控制台。仓库既有的判断也一致：两人阶段"不先做完整在线 IDE"（[可行性 §8](../docs/30-warehouse-product-feasibility.md)）。
4. **CDC 建议不在一期做**，先立项验证；先决条件多（binlog/GTID/权限/中间件/许可），既有文档已把它列为 P1/P2 单独立项。
5. **字段重命名有真实风险**：它会同时影响结构漂移审阅、质量规则、数据集契约与列级授权。方案是"RAW 不可变 + ODS 映射版本化 + 下游兼容检查"，不是改列名。
6. **已入湖数据查看页面是当前最明显的缺口**：资产目录只展示元数据（状态、行数、字节、结构哈希），点开资产也只有 schema/主键/哈希，**没有任何入口能看到行数据**；行级数据只能通过已发布数据集的受控查询看到。这是本方案优先级最高的交付项之一。

## 2. 目标与非目标

**目标**

- 单表/多表选择接入，逐表选择抽取策略，并在页面确认范围与字段口径。
- 增量接入：按水位列做半开窗口增量，可回溯、可对账、迟到可补偿。
- 以"登记式 SQL"表达无法用表名描述的范围（视图、过滤条件、必要的列裁剪/表达式），且可控、可审计、可回滚。
- 字段重命名/映射：源列 → 标准列的版本化映射，RAW 原件不变，下游契约与授权显式跟随。
- 已入湖数据查看：在授权与审计前提下，能在页面上查看 RAW/ODS 抽样明细、结构、批次与来源时间。

**非目标（本期明确不做）**

- 任意 SQL 查询控制台、任意 DDL/DML、跨库 JOIN 接入、把业务口径计算放进接入层。
- 无源库负载评估的"默认增量"：策略必须逐表证明，并记录依据。
- 一期 CDC/实时湖表（先立项验证，见 §3.3）。
- 明细数据的无限制导出、无审计浏览、绕过行列授权查看。

## 3. 方案

### 3.1 表级接入（扩展既有通道）

保留 `MYSQL_SNAPSHOT` 通道类型，补齐三件事：

1. **范围确认页升级**：探测结果表格从"只读清单"变成"可编辑接入范围"——每行可设置 `接入状态`（READY/BLOCKED/DISABLED）、`抽取策略`、`水位列`、`必填`。提交时随 `activate` 一并发给服务端校验，写入不可变清单版本。
2. **逐表策略**：`FULL_SNAPSHOT`（现状）与新增 `UPDATED_AT_KEYSET`（水位增量）。策略属于"批准清单"，因此策略变更 = 新清单版本 + 重新预检，不允许静默修改（与现有清单不可变语义一致）。
3. **表级元数据**：把源表主键、唯一键、行数估计、是否有水位列（候选列 + 类型 + 是否有索引）在确认页展示，作为选择策略的依据；无主键表的增量必须有显式风险提示。

### 3.2 增量（水位）策略

- 语义：按水位列取**半开窗口** `[上次水位, 本次上界)`，窗口边界与业务时区一起记录；同一窗口重复执行必须幂等（沿用现有批次幂等键）。
- 水位列必须显式登记：`column` + 类型 + 时区语义（UTC/本地）+ 是否单调。仅凭列名含 `update_time` 不得默认可用。
- 边界与陷阱（必须在方案评审时逐条确认，不能默认成立）：
  - 源库时间回拨/批量补数导致水位倒退 → 需重叠回读窗口（overlap）与对账。
  - 只更新不改水位的表（例如状态位更新未刷新时间戳）→ 水位增量会漏数，必须由业务确认或改用对账策略。
  - 硬删除无法被水位捕获 → 需要删除语义（逻辑删除标志 / 定期全量对账）。
  - 迟到与乱序 → 迟到补偿窗口 + 人工回看，禁止把"当日全量"当作迟到兜底。
- 参考：dbt 对源表新鲜度的 `loaded_at_field` 与 `warn_after/error_after` 建模方式可作为"水位列 + 新鲜度阈值"的登记口径（[dbt sources](https://docs.getdbt.com/docs/build/sources)）。
- 对账：新增 `RECONCILIATION`（枚举里已有同类）用于按主键抽样比对源与湖，输出差异报表而不是静默覆盖。

### 3.3 CDC（日志型增量）——建议单独立项

- 能力与代价：Debezium MySQL 连接器读 binlog，产出 INSERT/UPDATE/DELETE 变更事件，支持初始一致快照、增量快照（分块 + 水位 + 冲突消解）与结构变更事件（[Debezium MySQL 连接器文档](https://debezium.io/documentation/reference/stable/connectors/mysql.html)）。
- 前置条件（缺一不可，且都超出平台自身）：binlog 开启与保留期、GTID/行格式、专用只读账号与复制权限、中间件（Kafka Connect 或 Debezium Server）、事件存储与重放、运维责任人与容量。
- 结论：**一期不做**。触发条件写清楚：出现"水位增量无法覆盖且业务确实需要分钟级"的真实需求，且源库允许日志读取；届时按 PoC → 固定版本 → 许可与安全门禁 → 独立决策的流程走（与[可行性 §7.3](../docs/30-warehouse-product-feasibility.md)一致）。

### 3.4 受限 SQL 定义（"写 SQL 接入"的正确形态）

平台硬约束：**不允许任意用户 SQL**（参数化取值、标识符白名单、服务端行列访问、强制限额）。因此设计要点：

| 约束 | 设计 |
|---|---|
| 只读 | 只允许单条 `SELECT`（含 `WITH`）；服务端做语句白名单解析，出现 DDL/DML/多语句/注释绕过/`INTO OUTFILE`/`LOAD_FILE` 等一律拒绝 |
| 参数化 | 时间窗口、水位、分页、批次等只能是**占位参数**由平台注入，SQL 文本里不出现用户输入拼接 |
| 强制边界 | 必须包含水位列投影与 `WHERE` 水位条件（增量模式）或显式全量标记；平台强制 `LIMIT`/超时/最大行数/最大字节 |
| 标识符白名单 | 只允许已批准库/表；`information_schema` 之外的跨库访问默认拒绝 |
| 版本化与评审 | SQL 文本作为**接入定义版本**保存：提交 → 预检（语法、权限、执行计划与代价、抽样行数与耗时）→ 评审人批准 → 启用；历史版本只读保留 |
| 可回滚 | 启用新版本 = 新通道版本；旧版本执行记录与原件不被改写 |
| 审计 | 保存谁在何时启用哪个 SQL 摘要（保存文本哈希与版本，不在日志里打印 SQL 全文或数据） |

产品形态建议：**SQL 不是给用户随手跑查询的编辑器，而是"范围定义"的一种表达**——放在接入向导的"采集规则"步骤，与表清单并列，作为 `MYSQL_SNAPSHOT` 的一个可选来源模式（例如 `SOURCE_MODE = TABLE_LIST | REGISTERED_SQL`）。这与[可行性 §8](../docs/30-warehouse-product-feasibility.md)"不先做完整在线 IDE、模型 SQL 以 Git 审核为准"的判断一致。

**门禁**：任何新增组件都必须走既有流程——ADR + PoC + 固定版本 + 许可/安全/传递依赖检查 + 运维责任人 + 回退路径。

### 3.6 字段重命名与映射

分三层，绝不混用：

```text
源表列 (RAW，不可变原件：schema_json + raw_sha256)
   │  映射定义（版本化，按通道版本）
   ▼
标准列 ODS（target_column、类型、空值/默认、脱敏、单位/时区、是否对外）
   │  数据集契约字段（对外名称与语义，需授权）
   ▼
已发布数据集 release（列级授权 + 查询/导出）
```

- **映射对象**：`source_column → target_column`，加类型转换、空值/默认值、脱敏规则、是否对外可见、单位/时区换算。**一对一/多对一允许，一对多禁止**（禁止在接入层炸行导致行数语义变化）。
- **不进映射的**：业务口径计算、聚合、跨表 JOIN、去重规则——这些属模型层，避免"接入层偷偷改数"。
- **版本与影响**：映射随通道版本；修改映射 = 新版本 + 影响预览（受影响的清单版本、下游数据集/质量规则/授权列）+ 显式切换，正在执行的批次不被改写。
- **校验**：映射的源列必须存在于当前批准清单的 `schema_json`；源列消失/改名 → 结构漂移流程（`SCHEMA_CHANGE_REVIEW_REQUIRED`）而不是静默丢列。
- **下游联动**：质量规则、数据集契约字段、列级授权、查询审计都以标准列名为准；重命名必须同时给出下游兼容结论（新增列/弃用列/需要下游确认）。
- **RAW 不变**：原件与原始 schema 永久保留，重命名只作用于 ODS 及之后；任何"回到原始列名"的重放都必须可行。

### 3.7 已入湖数据查看（页面设计）

分三档，权限递增：

| 档位 | 内容 | 谁可以看 | 约束 |
|---|---|---|---|
| A 元数据（现状） | 名称、类型、状态、行数、字节、结构、主键、哈希、批次、来源时间 | VIEWER | 已实现 |
| B 抽样预览（新增） | 前 N 行、按列的类型与标准列名对照、空值率、采样时间 | ENGINEER 及以上；按源表逐表授权 | 强制抽样行数上限、超时、只读；不返回全量；访问写审计 |
| C 定向查行（新增，可选） | 按主键/业务键查单条或小集合 | 需显式列授权 + 行范围策略 | 参数化，禁止自由 SQL；命中记录写审计；敏感列脱敏 |

页面落点（复用现有信息架构，不新增菜单）：

1. **资产目录 → 资产详情**新增页签：`概览`（现状元数据）/ `结构`（源列 ↔ 标准列映射对照，含漂移历史）/ `数据预览`（B 档）/ `批次与来源`（每次运行的窗口、行数、哈希、结构版本）。
2. **数据预览**页：列头显示 `标准列名（源列名）` + 类型 + 脱敏标记；正文为抽样表格；工具栏给出"本次抽样条件 + 行数 + 时间 + 是否截断"；**明确标注这是抽样，不是全量**（避免把截断当全量）。
3. **RAW 与 ODS 切换**：默认展示 ODS（标准列）；RAW 需额外权限，并显示原始列名与原始类型。
4. **空/无权限/超大/失败**四态显式设计：无权限时不泄露列名与行数（与既有"目录可见≠可执行"一致）。
5. 与**数据服务**的边界：浏览是"工程排查"，数据集查询是"业务消费"（固定 release、行列授权、可导出）。两者在页面上明确区分，避免用浏览页绕过发布与授权。

## 4. 数据模型与迁移草案（V027+，仅草案）

不改动 V001–V026；全部为追加迁移：

- `warehouse.source_column_mapping`（或挂在 `warehouse.channel_version.config` 内并配单独审计表）：mapping 版本、源列、标准列、类型、空值/默认、脱敏、是否对外、创建人、原因。
- `warehouse.extraction_definition`：SQL 模式的范围定义（SQL 文本哈希、文本密文/受限读取、参数声明、评审状态、预检结果、启用版本）。
- `lake.object_watermark`：逐表水位状态（上次成功水位、重叠窗口、最近对账结果、依据与负责人）。
- `warehouse.preview_audit`：谁在何时以何种条件预览了哪张表/哪些列、返回行数、是否截断。
- `warehouse.source_object` 现有 `strategy` 不变，扩充取值语义文档；`state` 增加 `NEEDS_REVIEW` 之类需评审状态前必须有迁移与回退说明。

原则不变：**迁移显式执行、可前向修复、不自动改 Schema、不 DROP、不复用编码**。

## 5. 分期与验收

| 阶段 | 交付 | 验收（可复现） | 优先级 |
|---|---|---|---|

| P1-3 | 登记式 SQL 范围定义（只读、参数化、评审、预检） | 拒绝 DDL/DML/多语句/越库；预检给出代价与抽样；版本切换保留历史 | 中 |
| P2 | 对账策略（RECONCILIATION）+ 差异报表 | 主键抽样比对有差异清单；不静默覆盖 | 中 |
| P2/立项 | CDC | 独立 PoC + 门禁 | 低（先立项） |

每阶段都必须覆盖既有数据正确性要求：重复重放、迟到、重开、日期边界、缺快照、零分母语义，以及"不得把日均值/快照累加成月"。

## 6. 风险与未决问题（需业务/用户确认）

1. **水位列是否可靠**：逐表确认是否存在"更新不刷时间戳""时间戳由应用写入而非数据库""时区不一致"。没有确认前不得启用增量。
2. **删除语义**：源库硬删除如何发现（逻辑删除标志？定期对账？），是否需要"删除也入湖"。
3. **源库负载与窗口**：增量/对账/首次全量的允许时段、并发上限、是否允许加索引（只读账号通常不允许）。
4. **SQL 登记的责任人**：谁提交、谁评审、谁批准启用；是否需要"SQL 只在 Git 中评审、平台只登记批准结果"的更严格模式。
5. **脱敏与保留**：哪些列必须脱敏（手机号/邮箱/身份证）、原始数据保留期与备份范围。
6. **浏览权限边界**：谁能看 RAW（是否只限平台管理员）、是否需要"查看即审批"、是否允许导出。
7. **性能目标**：单表最大行数/字节、每日窗口时长、预览响应时间目标；没有实测数据前不写承诺值。
