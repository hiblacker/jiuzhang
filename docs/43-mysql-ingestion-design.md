## 0. 需求与结论

用户提出的四件事：**按表接入**、**写 SQL 接入**、**其它成熟接入方式**、**字段重命名**，以及接入后**有页面能查看已入湖数据**。

结论先行：

1. **按表接入基本已具备**，缺的是"逐表策略"与"字段口径"，属增量扩展而不是新建通道类型。
2. **增量（水位）接入是当前最该补的能力**：数据库层已预留 `UPDATED_AT_KEYSET` 策略枚举，但 Worker 只实现全量快照。
3. **"写 SQL 接入"确认为核心能力，且仓库里已有 PoC 证据**：`poc/component/st/jobs/*.json` 的 SeaTunnel JDBC 任务已用 `query` 表达"列裁剪 + 列别名 + 水位半开窗口 + 批次列"，正是本方案要的产品形态。因此 SQL 接入**升级为 P0**，执行层优先复用 SeaTunnel `Jdbc` source（见 §3.4、§3.8）。
4. **"写 SQL 接入"要做成"登记式 SQL 定义 + 受限执行"**：平台硬约束不允许任意用户 SQL（见 §3.4）。交互参照 DataEase 自定义 SQL 数据集（选库、SQL 编辑区、**保存前预览**、动态传参、字段重命名/改类型/计算字段），但**不引入 DataEase**：其社区版许可为 **GPL-3.0**（GitHub API 实测 2026-09-17），与"宽松许可优先、不强制本项目开源"的治理规则冲突，只能借鉴交互。
5. **CDC 建议不在一期做**，先立项验证；先决条件多（binlog/GTID/权限/中间件/许可），既有文档已把它列为 P1/P2 单独立项。
6. **字段重命名有真实风险**：它会同时影响结构漂移审阅、质量规则、数据集契约与列级授权。方案是"RAW 不可变 + ODS 映射版本化 + 下游兼容检查"，不是改列名；SQL 模式下列别名即映射的第一来源。
7. **已入湖数据查看页面是当前最明显的缺口，也是 SQL 接入的预览入口**：资产目录只展示元数据（状态、行数、字节、结构哈希），点开资产也只有 schema/主键/哈希，**没有任何入口能看到行数据**；行级数据只能通过已发布数据集的受控查询看到。列为第一优先交付。

## 2. 目标与非目标

**目标**

- 单表/多表选择接入，逐表选择抽取策略，并在页面确认范围与字段口径。
- 增量接入：按水位列做半开窗口增量，可回溯、可对账、迟到可补偿。
- 以"登记式 SQL"表达无法用表名描述的范围（视图、过滤条件、必要的列裁剪/表达式），且可控、可审计、可回滚。
- 字段重命名/映射：源列 → 标准列的版本化映射，RAW 原件不变，下游契约与授权显式跟随。
- 已入湖数据查看：在授权与审计前提下，能在页面上查看 RAW/ODS 抽样明细、结构、批次与来源时间。

**非目标（本期明确不做）**

- 任意 SQL 查询控制台（对任意库自由查询）、任意 DDL/DML、跨库与系统库访问、把对外指标口径的**定义**放进接入层（口径仍归模型层）。
- 无源库负载评估的"默认增量"：策略必须逐表证明，并记录依据。
- 一期 CDC/实时湖表（先立项验证，见 §3.3）。
- 明细数据的无限制导出、无审计浏览、绕过行列授权查看。

## 3. 方案

### 3.1 表级接入（扩展既有通道）

保留 `MYSQL_SNAPSHOT` 通道类型，补齐三件事：

1. **范围确认页升级**：探测结果表格从"只读清单"变成"可编辑接入范围"——每行可设置 `接入状态`（READY/BLOCKED/DISABLED）、`抽取策略`、`水位列`、`必填`。提交时随 `activate` 一并发给服务端校验，写入不可变清单版本。
2. **逐表策略**：`FULL_SNAPSHOT`（现状）与新增 `UPDATED_AT_KEYSET`（水位增量）。策略属于"批准清单"，因此策略变更 = 新清单版本 + 重新预检，不允许静默修改（与现有清单不可变语义一致）。
3. **表级元数据**：把源表主键、唯一键、行数估计、是否有水位列（候选列 + 类型 + 是否有索引）在确认页展示，作为选择策略的依据；无主键表的增量必须有显式风险提示。

### 3.2 增量（水位）策略

- 语义：按水位列取**半开窗口** `[上次水位, 本次上界)`，窗口边界与业务时区一起记录；同一窗口重复执行必须幂等（沿用现有批次幂等键）。
- 水位列必须显式登记：`column` + 类型 + 时区语义（UTC/本地）+ 是否单调。仅凭列名含 `update_time` 不得默认可用。
- 边界与陷阱（必须在方案评审时逐条确认，不能默认成立）：
  - 源库时间回拨/批量补数导致水位倒退 → 需重叠回读窗口（overlap）与对账。
  - 只更新不改水位的表（例如状态位更新未刷新时间戳）→ 水位增量会漏数，必须由业务确认或改用对账策略。
  - 硬删除无法被水位捕获 → 需要删除语义（逻辑删除标志 / 定期全量对账）。
  - 迟到与乱序 → 迟到补偿窗口 + 人工回看，禁止把"当日全量"当作迟到兜底。
- 参考：dbt 对源表新鲜度的 `loaded_at_field` 与 `warn_after/error_after` 建模方式可作为"水位列 + 新鲜度阈值"的登记口径（[dbt sources](https://docs.getdbt.com/docs/build/sources)）。
- 对账：新增 `RECONCILIATION`（枚举里已有同类）用于按主键抽样比对源与湖，输出差异报表而不是静默覆盖。

### 3.3 CDC（日志型增量）——建议单独立项

- 能力与代价：Debezium MySQL 连接器读 binlog，产出 INSERT/UPDATE/DELETE 变更事件，支持初始一致快照、增量快照（分块 + 水位 + 冲突消解）与结构变更事件（[Debezium MySQL 连接器文档](https://debezium.io/documentation/reference/stable/connectors/mysql.html)）。
- 前置条件（缺一不可，且都超出平台自身）：binlog 开启与保留期、GTID/行格式、专用只读账号与复制权限、中间件（Kafka Connect 或 Debezium Server）、事件存储与重放、运维责任人与容量。
- 结论：**一期不做**。触发条件写清楚：出现"水位增量无法覆盖且业务确实需要分钟级"的真实需求，且源库允许日志读取；届时按 PoC → 固定版本 → 许可与安全门禁 → 独立决策的流程走（与[可行性 §7.3](../docs/30-warehouse-product-feasibility.md)一致）。

### 3.4 登记式 SQL 接入（"写 SQL 接入"，P0 核心）

**产品定位**：SQL 不是"随手跑查询的控制台"，而是**抽取范围与字段口径的定义**，与表清单并列，作为 MySQL 通道的一种来源模式（`SOURCE_MODE = TABLE_LIST | REGISTERED_SQL`）。区别必须写清楚：DataEase 的自定义 SQL 是**查询定义**（直连源库、读时执行、结果用于图表）；九章的 SQL 是**抽取定义**（定时/增量执行、落 RAW/ODS、进批次与资产、可重放、可发布）。

**仓库内已有的实现证据**（不是设想）：`poc/component/st/jobs/objects.json`、`events.json` 是 POC-01 实际使用的 SeaTunnel 2.3.13 任务，其中的 `Jdbc` source 已经做到：

```json
"query": "SELECT id, project_id, ..., DATE_FORMAT(updated_at,'%Y-%m-%d %H:%i:%s') AS updated_at,
          '__BATCH__' AS batch_id
   FROM story
  WHERE updated_at > '__CURSOR__' AND updated_at <= '__UPPER__'
  ORDER BY updated_at, id",
"fetch_size": 10
```

即：**列裁剪 + 表达式/别名（字段重命名与类型规范化）+ 水位半开窗口（增量）+ 批次列 + 有界 fetch**，且整条 SQL 是模板，参数由平台注入（`__CURSOR__`/`__UPPER__`/`__BATCH__`）。这与本方案的安全模型天然一致：**SQL 由平台生成/校验，用户只填受控片段**。

**交互设计（参照 DataEase 自定义 SQL 数据集，实测其文档 2026-09-17）**：

| DataEase 的做法 | 九章采用 | 九章必须补齐的差异 |
|---|---|---|
| 选数据源 → 拖「自定义 SQL」→ SQL 编辑区（支持注释） | 同样：选已批准连接/库 → SQL 编辑区（Monaco 类编辑器、语法高亮、注释） | 编辑器只对**已批准库表**做联想；跨库/系统库不给联想 |
| 【预览数据】按钮 | 同样：**保存前预览**（强制 `LIMIT`，显示列名/类型/抽样行/耗时/是否截断） | 预览结果同样受列级脱敏与审计约束 |
| 动态传参 `$DE_PARAM{field = '$[xxx]'}`，参数类型/生效模式/默认值，系统自动识别变量；时间范围用两个参数 | 采用同类机制：**平台占位参数**（`{{window_start}}`/`{{window_end}}`/`{{cursor}}`/`{{batch_id}}`/`{{timezone}}`），变量从 SQL 自动识别并展示 | 占位参数**只能由平台注入**，禁止在 SQL 里出现未声明的 `${用户输入}`；不提供"仅编辑时生效"这类会导致语义漂移的开关 |
| 字段重命名、改类型、日期解析、计算字段（表达式+语法校验）、分组、复制、删除 | 采用"结果列契约"：SQL 的 `AS` 别名即 ODS 标准列初值；页面再允许覆盖标准列名/类型/脱敏/是否对外；**计算字段允许在 SQL 内表达**，但不在接入层提供可视化表达式编辑器（属模型层职责） | 列改名/改类型必须产生新版本 + 影响预览；计算字段不得改变行数（禁止炸行/聚合改变粒度） |
| 行列权限属 X-Pack 企业版 | 行列授权是平台内建能力（已有），接入层只登记"哪列对外" | 预览与浏览同样走行列授权 |
| 数据关联（左/右/内/全连接，Calcite 跨源） | **允许在 SQL 抽取里 JOIN**（2026-09-17 决策：只读查询一律允许）；平台要求声明粒度与唯一键、确认增量驱动表 | 不照搬 Calcite 跨源联邦查询：只在**同一数据源**内 JOIN |

**安全矩阵（执行侧硬约束，缺一不可）**：

| 约束 | 实现 |
|---|---|
| 只读 | 单条 `SELECT`（含 `WITH`）；语句白名单解析，拒绝 DDL/DML/多语句/注释绕过/`INTO OUTFILE`/`LOAD_FILE`/存储过程调用 |
| 参数化 | 时间窗口、水位、批次、时区只能来自平台占位参数；SQL 文本中不得拼接请求参数 |
| 强制边界 | 平台注入 `LIMIT`/`fetch_size`；服务端超时、最大行数、最大字节、最大执行时长；超限明确拒绝而不是截断后当全量 |
| 标识符白名单 | 仅已批准库表；默认拒绝跨库与系统库访问 |
| 只读账号 | 每来源一套最小权限只读账号（现有角色边界不变），凭证只以引用形式下发 Worker |
| 版本化与评审 | SQL 文本哈希 + 版本 + 提交人 + 评审人 + 原因；启用 = 新通道版本，历史版本只读保留 |
| 可回滚 | 停用版本即回到上一版本；已执行批次与原件不被改写 |
| 审计 | 记录谁在何时启用/预览了哪个 SQL 版本、返回行数与耗时；日志不打印 SQL 全文与数据行 |
| 幂等 | 抽取 SQL 必须可重复执行（水位半开窗口 + 批次键）；同一窗口重复执行不产生重复资产 |

**执行路径的两条路线（需在批准前选一）**：

- **路线 1（推荐先做）：复用 SeaTunnel `Jdbc` source 执行 SQL 抽取**。POC-01 已验证该路径能表达水位窗口、别名与批次列（见上），且 SeaTunnel 是既有批准候选（Apache-2.0、锁文件、镜像固定）。平台把批准的 SQL 模板 + 参数注入为一次 SeaTunnel 作业，自身仍管批次、清单、资产与发布。
- **路线 2：在现有 Node Worker 内实现受控 JDBC 适配器**（复用 `tools/lake-ingest.mjs` 的批次/哈希/清单语义）。优点是不新增常驻组件、与现有资产契约完全一致；代价是自研 SQL 校验、类型映射与增量执行。
- 两条路线**不并行维护**（[33 号设计 §64](../docs/33-lake-implementation-design.md) 的既有约束）。建议用一个小样表（含水位列、中文字段、`DECIMAL(20,2)`、时间戳）做对照验证后选一，并把结论写入 ADR。

### 3.6 字段重命名与映射

分三层，绝不混用：

```text
源表列 (RAW，不可变原件：schema_json + raw_sha256)
   │  映射定义（版本化，按通道版本）
   ▼
标准列 ODS（target_column、类型、空值/默认、脱敏、单位/时区、是否对外）
   │  数据集契约字段（对外名称与语义，需授权）
   ▼
已发布数据集 release（列级授权 + 查询/导出）
```

- **映射对象**：`source_column → target_column`，加类型转换、空值/默认值、脱敏规则、是否对外可见、单位/时区换算。**一对一/多对一允许，一对多禁止**（禁止在接入层炸行导致行数语义变化）。
- **映射层不做的事**：聚合、跨表 JOIN、去重——这些可以在 SQL 抽取里表达，但不能藏在映射规则里，避免"映射偷偷改数"。
- **版本与影响**：映射随通道版本；修改映射 = 新版本 + 影响预览（受影响的清单版本、下游数据集/质量规则/授权列）+ 显式切换，正在执行的批次不被改写。
- **校验**：映射的源列必须存在于当前批准清单的 `schema_json`；源列消失/改名 → 结构漂移流程（`SCHEMA_CHANGE_REVIEW_REQUIRED`）而不是静默丢列。
- **下游联动**：质量规则、数据集契约字段、列级授权、查询审计都以标准列名为准；重命名必须同时给出下游兼容结论（新增列/弃用列/需要下游确认）。
- **RAW 不变**：原件与原始 schema 永久保留，重命名只作用于 ODS 及之后；任何"回到原始列名"的重放都必须可行。

### 3.7 已入湖数据查看（页面设计）

分三档，权限递增：

| 档位 | 内容 | 谁可以看 | 约束 |
|---|---|---|---|
| A 元数据（现状） | 名称、类型、状态、行数、字节、结构、主键、哈希、批次、来源时间 | VIEWER | 已实现 |
| B 抽样预览（新增） | 前 N 行、按列的类型与标准列名对照、空值率、采样时间 | ENGINEER 及以上；按源表逐表授权 | 强制抽样行数上限、超时、只读；不返回全量；访问写审计 |
| C 定向查行（新增，可选） | 按主键/业务键查单条或小集合 | 需显式列授权 + 行范围策略 | 参数化，禁止自由 SQL；命中记录写审计；敏感列脱敏 |

页面落点（复用现有信息架构，不新增菜单）：

1. **资产目录 → 资产详情**新增页签：`概览`（现状元数据）/ `结构`（源列 ↔ 标准列映射对照，含漂移历史）/ `数据预览`（B 档）/ `批次与来源`（每次运行的窗口、行数、哈希、结构版本）。
2. **数据预览**页：列头显示 `标准列名（源列名）` + 类型 + 脱敏标记；正文为抽样表格；工具栏给出"本次抽样条件 + 行数 + 时间 + 是否截断"；**明确标注这是抽样，不是全量**（避免把截断当全量）。
3. **RAW 与 ODS 切换**：默认展示 ODS（标准列）；RAW 需额外权限，并显示原始列名与原始类型。
4. **空/无权限/超大/失败**四态显式设计：无权限时不泄露列名与行数（与既有"目录可见≠可执行"一致）。
5. 与**数据服务**的边界：浏览是"工程排查"，数据集查询是"业务消费"（固定 release、行列授权、可导出）。两者在页面上明确区分，避免用浏览页绕过发布与授权。

### 3.8 原始组件线（SeaTunnel / DolphinScheduler）现状与接回选项

- **没有丢，也没有被删除**：全历史 `git log --diff-filter=D` 中没有 SeaTunnel/DolphinScheduler 文件删除记录；组件 PoC 完整保留在 `poc/component/`——SeaTunnel 2.3.13（`Dockerfile.st`、`st/`、两个 JDBC 作业）、**DolphinScheduler 3.4.3 standalone**（即"另一个服务"，调度编排）、MySQL 8.0.43、PostgreSQL 16.15 与 dbt 适配层，版本锁在 `poc/component/dependencies.lock.json`。
- **为什么当前运行的栈里看不到**（权威表述）：
  - [37 号验收](../docs/37-phase-one-acceptance.md)：正式 MySQL 接入采用既有 MySQL CLI 的单只读事务读取、由 Node Worker 执行，**未把 SeaTunnel 合成 PoC 冒充正式接入**；**DolphinScheduler 正式产品适配没有完成**，也不与本地驱动同时启用（现用 `LAKE_CALENDAR_DRIVER=local`）。
  - [33 号设计](../docs/33-lake-implementation-design.md)：核验 SeaTunnel 适配能否表达共享快照、类型保真与取消；不足时在同一 Worker 契约下实现受控 JDBC 适配，**不并行维护两套完整链路**。
  - [可行性 §7.3](../docs/30-warehouse-product-feasibility.md)：先沿用 DS + dbt v1 做正式化验证，不同时增加 Dagster/Kestra/NiFi/Hop。
- **真正丢失的部分（如实说明）**：POC-01 的**完整端到端运行报告**原先写在被忽略的 `work/poc01-*.json`，该文件在 2026-09-15 的一次检出检查中已不存在（`poc/component/README.md` 自述此点）。保留下来的只有锁定文件、作业配置、运行脚本与冒烟记录（SeaTunnel FakeSource→Console、DS standalone 启动）。即"组件可运行"有证据，"整链路验收"只剩历史摘要。

| 选项 | 内容 | 收益 | 代价/前置 |
|---|---|---|---|
| A 维持现状 | 自研 Worker + 内置日历；SeaTunnel 仅作候选 | 无新增常驻组件，资产契约单一 | SQL 抽取、水位增量、CDC 全需自研 |
| B 接回 SeaTunnel 作执行层（**推荐，先做 SQL 部分**） | 平台生成作业配置（复用 POC-01 模板：`query` + 占位参数），SeaTunnel 执行抽取，平台仍管批次/清单/资产/发布 | SQL 接入与增量立刻有成熟执行器；CDC 有现成连接器路径 | 需固定镜像与许可复核（Apache-2.0 已锁）；新增执行组件的资源与故障域；需对照验证类型保真与幂等 |
| C 再接回 DolphinScheduler 做外部调度 | 用 DS 触发既有 `external` 日历入口 | 复杂 DAG/依赖编排 | 与内置日历重复；DS 产品适配未完成需重新立项；当前无多源 DAG 需求证据 |

建议：**B 的 SQL 抽取部分优先**（直接服务"写 SQL 接入"这一核心需求），**C 暂不接回**。

## 4. 数据模型与迁移草案（V027+，仅草案）

不改动 V001–V026；全部为追加迁移：

## 5. 分期与验收

| 阶段 | 交付 | 验收（可复现） | 优先级 |
|---|---|---|---|
| P0-1 | 已入湖数据**抽样预览**页（B 档）+ 预览审计（同时作为 SQL 接入的"保存前预览"） | 合成源表 10 万行：预览返回 N 行且标注截断；无权限身份看不到列名与行数；审计含身份/表/列/行数/请求 ID | 最高 |
| P0-2 | **登记式 SQL 接入**：SQL 编辑器 + 保存前预览 + 占位参数 + 结果列契约 + 版本化评审 + 受限执行（先按 §3.4 路线 1/2 做对照验证并写 ADR） | 拒绝 DDL/DML/多语句/越库/拼接参数；预览与执行都强制限额；同一 SQL 版本可重放且幂等；版本切换保留历史与原件；对照验证覆盖水位窗口、别名、中文列、`DECIMAL(20,2)`、时间戳 | 最高（核心需求） |
| P0-3 | 范围确认页升级（逐表启用/策略/水位列）+ 结构对照页签 | 关表后不再抽取；水位列候选展示；结构漂移触发审阅而非静默丢列 | 高 |

| P1-2 | 字段重命名与映射（通道版本化 + 影响预览；SQL 模式下列别名为初值） | 重命名后 ODS 标准列正确、RAW 原件不变、下游契约与授权显式跟随、回放可用 | 高 |

## 6. 风险与未决问题（需业务/用户确认）

1. **水位列是否可靠**：逐表确认是否存在"更新不刷时间戳""时间戳由应用写入而非数据库""时区不一致"。没有确认前不得启用增量。
2. **删除语义**：源库硬删除如何发现（逻辑删除标志？定期对账？），是否需要"删除也入湖"。
3. **源库负载与窗口**：增量/对账/首次全量的允许时段、并发上限、是否允许加索引（只读账号通常不允许）。
4. **SQL 登记的责任人**：谁提交、谁评审、谁批准启用；是否需要"SQL 只在 Git 中评审、平台只登记批准结果"的更严格模式。
5. **脱敏与保留**：哪些列必须脱敏（手机号/邮箱/身份证）、原始数据保留期与备份范围。
6. **浏览权限边界**：谁能看 RAW（是否只限平台管理员）、是否需要"查看即审批"、是否允许导出。
7. **性能目标**：单表最大行数/字节、每日窗口时长、预览响应时间目标；没有实测数据前不写承诺值。
