# 九章实施方案：先完成整库与每日持续入湖

> 2026-09-15 按用户最新要求修订。按可运行结果验收，不估工时、不按人员排周计划。完整产品目标及公开产品研究见[分析报告](30-warehouse-product-feasibility.md)。

开发细节见[详细实施设计](33-lake-implementation-design.md)，可直接交给 Luna 的完整任务见[执行提示词](../LUNA_TASK.md)。

## 1. 首个交付目标

**把用户提供的 MySQL 业务库完整接入原始湖区，并持续接收每天的数据；每日文件到达采用同一套批次、版本、完整性和恢复机制。**

当前优先级是整库首次全量、每日运行、数据可追溯和失败可恢复。API、标准模型、指标、治理及丰富的页面仍是后续目标，按依赖逐项增加。原始入湖不等待业务状态、指标公式或报表口径全部确定。

“整库”默认包含指定业务库的全部基础表，包括字典表、关联表、日志表和空表；只连接指定库，不扩大到账号可见的其他库。视图单独登记并明确是否物化，存储过程、触发器和事件登记为源结构信息，不执行、不当作数据表抽取。权限不足、特殊类型、非事务表或不可读取对象必须进入阻断/例外清单，不能静默跳过后声称完成整库入湖。

首个系统要能回答：有哪些表，哪些已覆盖；最新完整批次是哪次、实际采集时点是什么；今天数据是否到齐；失败如何补跑；原件如何追溯和重新处理。

## 2. 实现顺序与退出条件

| 顺序 | 交付内容 | 通过条件 |
|---|---|---|
| A：全库清单与接入计划 | 读取指定库的表、字段、主键、类型、引擎与规模估计，生成覆盖清单 | 每个基础表都有明确策略；未支持项有原因；估计行数不冒充实测行数 |
| B：首次整库入湖 | 抽取所有计划表，保存原始记录、Schema、分片及清单，形成系统批次 | 全部必需表完成；空表有记录；分片可校验；重放可读；系统完成状态与表清单一致 |
| C：每日持续入湖 | 持久化日历与运行状态、调度、重试、缺批次发现、补跑、历史版本 | 连续窗口可执行；重复触发不重复提交；停机恢复能发现遗漏；失败保留上一完整批次 |
| D：每日文件入湖 | 指定目录发现、完整性判断、原件封存、文件批次与解析 | 新增、重复、迟到、更正、缺失、半写及断连均有正确状态；CSV/Excel/JSON/Parquet 逐项准入 |
| E：API 与数据加工 | API 分页/增量、明细和维度模型、质量规则、数据集发布 | 复用已有入湖资产与批次；加工失败可重读原件；不重建一套状态与调度 |

B、C 合起来才是首个系统入湖交付；一次导出成功不能当成持续接入完成。D 的日历、状态和版本契约从 A 开始共用，接入实现按顺序落地。

## 3. 为效率收敛技术路线

- 沿用现有 Java 控制 API、独立 Worker 和 PostgreSQL 元数据。原始湖区先采用持久化目录及不可变 manifest，留出对象存储接口。
- MySQL 读取复用现有 SeaTunnel 适配路线。进入整库执行前核验类型保真、快照边界和失败恢复；若连接器无法满足必需语义，补受控 JDBC 读取适配器。只完成一条主线，不并列开发多个引擎。
- 先形成可以真实运行的“整库入湖”操作，再补来源总览、表覆盖清单、批次详情三个必要页面。完整在线 IDE、拖拽 ETL、复杂治理界面后置。
- 调度只由一个执行入口驱动，复用既有 DolphinScheduler 路线；平台持久化应执行窗口和批次账本，用于重试去重及漏跑发现。后台调度不依赖网页保持打开。
- AI 按“契约与迁移 → 实现 → 自动检查 → 实际运行 → 修复 → 提交”连续完成切片，减少人为交接和重复研究；以真实结果决定下一步，不等待固定评审日或人员排期。
- 使用本机现有环境与国内源；新增依赖锁精确版本并检查许可，历史实验结果不足的部分只补与当前主线有关的验证。

本次允许修改方案、合成验收契约及接入预检输出；原始结构与数据只保留在忽略目录。正式实现修改范围按 A–E 各工作包落到控制 API、Worker、迁移和测试，已执行迁移不重写。

## 4. 首次整库如何保证覆盖与保真

### 4.1 先生成清单，再执行全量

清单记录源库范围、表 ID、类型、存储引擎、列序与类型、主键/唯一键、Schema 指纹、抽取方式及支持状态。系统批次固定引用清单版本，执行中新增表或改表必须产生结构变化记录，不能临时改变“全部完成”的分母。

信息模式中的行数用于规划，InnoDB 的 TABLE_ROWS 是估计数。完成统计以实际读取/落盘记录数为准；需要源端数量对账时，在相同快照边界内校验，不能拿抽取结束后的动态 COUNT 与先前快照硬比较。[MySQL 表统计说明](https://dev.mysql.com/doc/mysql-infoschema-excerpt/5.7/en/information-schema-tables-table.html)

### 4.2 原始层保留来源数据

按表分片流式写入，避免整库加载内存。首版规范可采用带独立 Schema 的 JSONL 分片：大整数与 Decimal 保留精确字符串和类型，二进制保留编码标识，时间值保留源类型/精度及会话时区；空值、空字符串、零值分别保存。特殊类型有可往返验证的编码后才能通过，不能静默截断、丢列或按普通浮点转换。

原始层不做业务过滤和多表关联。无主键表仍能全量封存；有主键不代表可以推断历史状态。每个分片记录行数、字节数、内容哈希、列结构版本与源读取边界，空表也有零行清单。

### 4.3 快照一致性必须显式记录

对满足条件的 InnoDB 表，首选同一只读 REPEATABLE READ 事务中的一致性读取，流式依次完成清单中的表；确认抽取器确实共享该快照后，才标记为同一时点的整库快照。多个独立连接不能默认共享一个快照。DDL、非事务表和长事务负载必须单独处理。[MySQL 一致性读取](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)、[单事务导出边界](https://dev.mysql.com/doc/refman/8.0/en/mysqldump.html)

若只能按表独立读取，系统批次标记“表级快照集合”，记录各表读取时间范围；跨表同一时点一致性不成立。整库覆盖完成与同一时点一致性是两个独立字段。需要更强一致性时采用经验证的一致性导出或全量与 CDC 衔接方案，不能只改完成状态。

连接中断后原事务快照已失效，不得接着上次主键继续读取并声称仍是同一快照。首版重新执行受影响的快照单元；要求整库同一时点时重新执行整个系统快照。旧分片保留为失败尝试，不混入新结果。

### 4.4 持久化后才提交批次

```text
发现清单 → 创建系统批次 → 分表抽取 → 暂存分片
  → 关闭写入并完成持久化校验 → 封存表清单
  → 核对全部必需表 → 提交系统清单 → 更新最新完整批次指针
```

指针使用数据库条件更新，防止旧任务覆盖新批次。文件与数据库没有共同事务：先持久化对象，再在数据库事务中登记引用及状态；崩溃后用账本协调已封存但未提交的对象，不能引用未写完的文件。共享盘/对象存储需验证对应提交语义，不能把改名直接当作所有介质都已持久化。

## 5. 每日数据库入湖是基础能力

### 5.1 先覆盖，再优化读取量

| 表的实际能力 | 初始策略 | 后续优化及限制 |
|---|---|---|
| 小表、字典表、无可靠增量条件 | 每次完整快照，保留历史版本 | 根据实测源库负载及存储量决定优化；无主键不阻塞原始封存 |
| 主键 + 已验证的更新时间 | 首次全量，之后按固定上界和重叠窗口读取 | 稳定排序和复合游标；按键处理回读；更新时间必须覆盖每次修改；时间游标不保证捕获硬删除 |
| 真正只追加且已验证游标语义 | 首次全量，之后增量与对账 | 自增 ID 可能先分配后提交，不能把最大 ID 当作绝对不漏数保证 |
| 需要完整新增/更新/删除事件 | 初始快照 + 经验证的 CDC | 需验证 binlog 权限、保留期、位点和全量衔接；日志缺口则重建基线 |
| 大表且全量超出可用运行窗口 | 记录阻断，核验索引、读取副本或 CDC | 不擅自改源库索引、不以漏表换“成功” |

首版默认从每日全量快照建立正确基线。逐表证明增量可用后再切换策略，切换时记录基线与新位置，支持退回全量；这不代表任何规模都适合每天全量。

每日快照保留当次完整状态，能够对比两个完整快照中行的出现/消失，但无法还原两次采集之间发生又撤销的修改。硬删除与“暂时查询不到/权限失效”必须区分；历史只从实际可观测时间开始，不能靠今天数据补造昨天快照。

### 5.2 调度账本与补跑

每个来源维护时区、触发时间、预期到达时间、窗口定义、并发上限、超时/重试、补跑规则、保留策略与启停状态。每天运行是可配置默认周期；时间窗口采用 `[开始, 结束)`，执行日期、源快照时点和业务日期分开保存。

系统维护 `(source_id, plan_version, scheduled_window)` 这一逻辑运行键；重试增加 attempt，主动修订增加 revision。定时触发、手工重跑和服务重启不能分别生成重复的成功结果。

- **漏跑：**调度恢复后比对应有窗口和实际账本，列出缺失窗口，按配置补跑并限制积压并发；不只触发当前一轮。
- **无历史可补：**昨天未采集、源库只有当前态时，今天重跑不能命名为昨天快照；记录缺失，另生成今天的补采，并标明实际数据时点。
- **无变化：**轮询成功但没有新增记录记 `NO_CHANGE`；它不同于没有执行、源不可达或没有收到文件。
- **表级失败：**记录失败对象及尝试，系统批次保持不完整；最新完整批次不前移，已成功原件可供排查。
- **断点：**只推进已封存输入的接收位置；解析/加工位置独立维护。错误页、失败文件或未提交分片不能推进完成水位。
- **并发与租约：**同一来源重叠窗口受控排队；失去租约的旧 Worker 不能提交批次或推进水位。
- **结构变化：**每轮发现新增、删除、改名和列类型变化。新增表自动进入待接入并安排基线抽取；删除/改名不清理旧湖数据，不悄悄降低覆盖要求。

## 6. 每日文件入湖与数据库共用账本

外部负责把文件放到 Worker 可读目录，传输工具不属于平台接入契约。管理员配置根目录、匹配规则、来源、预期交付模式及解析格式。

| 文件交付情况 | 必需行为 |
|---|---|
| 每天一份或一组完整文件 | 按交付日期/批次建立清单；多文件需要完成清单或明确闭合规则，单文件到达不能代表一组齐全 |
| 当天没有文件 | 有到达约定时标记 `MISSING/OVERDUE`；无到达约定只能标记“本次未发现”，不能判断漏交 |
| 合法空数据日 | 用零记录文件或明确的空交付标志确认 `EMPTY_CONFIRMED`；不能把未交文件当零数据 |
| 重复复制或改名 | 在同一逻辑交付版本内用内容哈希判重；保留观察记录，避免重复提交 |
| 同名文件被更正 | 新内容形成新版本，明确替代哪个交付版本；不覆盖历史原件 |
| 迟到或历史补交 | 记录业务日期与实际接收时间；按历史窗口修订，触发需要的下游重算 |
| 文件仍在写或目录断连 | 保持待接收/不可达状态，不发成功；恢复后完整补扫 |
| 持续追加到同一个文件 | 首版要求滚动生成封闭文件，或明确按稳定整文件版本接收；逐字节 tail 需另有偏移、截断和轮转契约 |

优先用完成清单、`.done` 标志或临时后缀原子改名判断交付完成。无法约定时，多轮大小/修改时间稳定及复制前后复核只能作为有限保证；强完整性来源必须有闭合信号。

原件在识别后先封存，CSV、Excel、JSON/JSONL、Parquet 分别维护解析契约。区分 `RAW_COMMITTED`（原件可靠保存）与 `PARSED`（结构化解析完成），不能把文件保存成功说成这种格式已经可以查询。

目录规划示例，尚未创建或部署：

```text
/data/inbox/<source>/                                        外部交付，Worker 只读
/data/jiuzhang/staging/<batch>/<attempt>/                     写入中的对象
/data/jiuzhang/raw/<source>/<object>/<batch>/<version>/       不可变原件及清单
/data/jiuzhang/quarantine/<batch>/<attempt>/                  错误说明与受控副本
```

按来源、对象和批次定位数据，日期仅用于分区与查找，不单独作为唯一 ID。原件、Schema、对象清单、运行账本和查询目录一起备份；保留期与清理另行配置，任何清理不能使已发布引用悬空。

## 7. 最小数据模型和运行界面

优先扩展已有来源、批次、检查点和租约表，避免另造一套状态系统。新增对象及字段通过后续版本迁移实现，以下是契约设计，不表示已有这些表。

| 对象 | 必须表达的内容 |
|---|---|
| Source / IngestionPlan | 指定库或目录、凭证引用、接入策略、调度、时区与计划版本 |
| Inventory / SourceObject | 固定清单版本、表/文件集、Schema、必需项、支持状态 |
| SystemBatch / ObjectBatch | 预期窗口、实际读取时段、快照一致性、覆盖数、状态、attempt/revision |
| RawObject / Manifest | 路径、格式、字节/行数、哈希、Schema、来源位置及持久化状态 |
| Checkpoint / DeliveryLedger | 已提交水位、应有/已到窗口、文件逻辑版本、租约与补跑关系 |

最小界面围绕真实接入展开：**来源总览 → 全库表覆盖 → 批次详情与历史 → 失败重试/补采 → 原始资产结构与受控预览**。关键统计是应接入表数、成功/失败/未覆盖数、最新完整批次、实际采集时点、缺失窗口、积压与数据量。任务成功数不能替代表覆盖率和数据完整性。

## 8. 首个系统的验收门槛

1. 清单中的全部必需基础表均入湖，包含空表；不存在未说明的跳过。视图及特殊对象有单独状态。
2. 持久化分片能按 manifest 校验并读取，类型和字段无静默损失；批次与原始来源可追溯。
3. 两个连续调度窗口能运行；同一窗口重复触发或失败重试不会重复提交。测试环境可用缩短周期验证机制，仍标明未经实际跨日长期运行验证。
4. 中断 Worker、失去租约、单表失败、目录断连或落盘失败时，旧完整批次仍可用；恢复后缺失窗口和失败原因可见。
5. 不能重建过去时点时明确记录缺失；不得用当前数据冒充历史补采成功。
6. 文件新增、空交付、缺失、重复、迟到、更正、多文件未齐和半写等场景均有验收样例。
7. 新增表与 Schema 变化可以发现；增量、删除、无主键、大数、二进制和时间类型边界有合成测试及必要的真实源验证。
8. 源库只读；敏感配置及原始数据不进 Git；源库负载、存储限额、备份恢复有实测结果。

## 9. 当前实测与下一执行入口

157 张表均已生成首批全量接入计划，无主键表不排除，尚未批准任何表的增量策略。真实结构及逐表清单仅在本地忽略目录保存；该发现阶段不读取业务行，后续执行结果单独记录在[实现与实际验收记录](34-lake-implementation-evidence.md)。
