# 九章两人实施方案

> 2026-09-15 建议执行版。依据[产品与可行性报告](30-warehouse-product-feasibility.md)，用于安排开发；排期是两人主要投入、样本及时到位的估算。

## 1. 做什么

建设通用数据仓库平台：**数据库、API、文件目录 → 原始湖区 → 标准明细与维度 → 汇总模型 → 可授权查询的数据集**。DevOps 是第一个验证主题，业务状态和公式只进入领域模型。

首个演示目标控制在：一张 MySQL 表、一个 REST 资源、一组 CSV，经过统一批次与资产协议，形成可查询、可重跑的数据集。完整一期再覆盖 Excel、JSON/JSONL、Parquet。

## 2. 技术路线直接收敛

| 部分 | 实施决定 |
|---|---|
| 控制 API | 沿用现有 Java/Spring Boot，负责来源、运行、资产、模型和发布管理 |
| 执行 | 沿用独立 Worker，所有抽取、解析和模型执行在后台完成 |
| 元数据及首期数仓 | PostgreSQL；元数据、开发结果、发布结果隔离，查询身份只读 |
| 原始湖区 | 先用持久化文件目录，平台生成不可变路径及 manifest；存储接口留出后续对象存储扩展 |
| MySQL | 先验证现有 SeaTunnel 路线；连接器准入和恢复语义不过关时，采用受控 JDBC 读取适配器，不能绕过同一验收 |
| REST API | 首版用 Worker 内的受控 HTTP 读取器，只支持固定分页模板；dlt 作为后续适配优化，不阻塞首版 |
| 文件 | 自研目录发现、版本登记和状态管理；格式解析复用固定版本、许可经检查的库 |
| 建模与调度 | 沿用既有 dbt v1 / DolphinScheduler 验证路线，经适配器关联平台运行 ID；不在本阶段迁移到其他整套平台 |
| 控制台 | 先做来源配置、批次详情、资产详情、模型运行、发布五个页面；前端框架按现有工程治理准入 |

所有新增依赖先记录精确版本及许可；使用本机环境和已配置国内源。当前已验证的版本与待验证候选必须分别登记。

## 3. 前六周怎么分工

人员 A 主负责控制面、权限、发布与页面；人员 B 主负责接入、湖区、模型与数据验证。每周共同核对输入、输出和故障用例。

| 时间 | 人员 A | 人员 B | 当周交付与验收 |
|---|---|---|---|
| 第 1 周 | 明确来源、资产版本、运行、发布契约；列出复用表及新增迁移；画五页操作流程 | 只读核验测试库连接与表结构；选一张业务键清楚的表；准备 CSV 和 API 合成样例 | 确定来源字段、主键、时间口径和预期结果；真实 API 未提供时明确采用模拟服务 |
| 第 2 周 | 实现资产版本、manifest 登记和运行关联；提供来源及批次最小页面 | 实现持久化湖区、目录轮询和 CSV 解析 | CSV 原件可保留并追溯；重复投递不重复计入；半写文件不提前发布 |
| 第 3 周 | 接入预检、运行日志摘要、失败重试页面；贯通控制 API 与执行适配 | 实现 MySQL 首次全量及有条件的增量读取 | 全量对账；重试不多算；无可靠增量字段时明确采用全量快照，不编造历史 |
| 第 4 周 | 模型版本登记、隔离构建、质量结果展示 | 完成一个 REST 分页模板、原响应留存和重试；建立首个明细与汇总模型 | 三类入口进入同一资产协议；API 中断能续跑；模型输出与黄金结果一致 |
| 第 5 周 | 发布状态、只读查询入口、资产详情和失败保旧 | 重复、迟到、修订及跨日期用例；补齐模型质量规则 | 候选结果失败时旧发布仍可查询；禁止旧运行覆盖新发布 |
| 第 6 周 | 串联五页流程，补操作说明与演示脚本 | Worker 重启、目录断连、API 限流、重算恢复联调 | 从创建来源到查询发布数据集完成一次独立操作；交付 0.1 演示版 |

时间不够时，保留“一表、一资源、一组 CSV”的边界，减少配置选项和页面装饰。原件、幂等、失败保旧及来源对账属于正确性要求，不能用省略这些要求换取演示完成。

## 4. 文件夹接入契约

建议部署路径如下，均为规划示例，尚未在机器创建：

```text
/data/inbox/<source>/                         外部放文件，Worker 只读
/data/jiuzhang/staging/<run>/                 平台复制与校验
/data/jiuzhang/raw/<source>/<asset-version>/  不可变原件及清单
/data/jiuzhang/quarantine/<run>/              平台错误记录及受控副本
```

处理顺序：扫描 → 确认交付完成 → 复制校验 → 登记原始资产 → 解析 → 质量检查 → 建模 → 发布。

- 优先约定完成标志或临时文件原子改名；无法约定时采用多轮稳定检查，并明确它不能保证生产方不会继续写入。
- 同名不同内容登记新版本；相同内容重试按来源和逻辑版本判断，不能跨业务批次全局去重。
- 每个来源明确追加、按键更新或完整快照，不能由平台猜测。
- 原件不自动删除、移动或覆盖；目录断连、坏文件、结构变化有可见状态和重新处理入口。
- 第 7 周起依次扩展 JSON/JSONL、Excel `.xlsx`、Parquet；`.xls` 如有真实需求补充准入与估算。四格式都必须有样例与预期结果。

## 5. 后续里程碑

| 版本 | 估算窗口 | 完成标准 |
|---|---|---|
| 0.1 首个闭环 | 第 4–6 周 | MySQL、一个 REST 模板、CSV 可入湖、建模、发布和查询 |
| 0.2 内部可用 | 第 12–18 周 | 四格式、常见分页、增量与修订、项目权限、模型质量、版本发布与基本页面 |
| 0.3 试运行交付 | 第 20–30 周 | 第二业务主题复用；容量、恢复、权限与试运行验收；完成运维交接 |

完整范围估算 **30–44 人周**。按两人全职、75% 有效投入折算约 **20–30 自然周**；外部样本及权限长期等待另计。没有真实容量画像前，不承诺吞吐和并发数。

## 6. 现在可以开工的第一个工作包

**WP-01：测试源核验与三类入湖契约，预算 2–3 个工作日。**

1. 使用已本地隔离保存的测试连接，只读验证连通、TLS、版本、表结构和权限；报告中只保留必要的脱敏结构结论。
2. 选一张有明确键的表；记录更新时间、删除表达和时间类型是否存在，不先假定任何业务含义。
3. 以合成数据准备 CSV、分页 API 输入及预期输出，真实 API 和文件样本到位后替换联调用例。
4. 定义 `source_position`、`asset_version`、`schema_version`、`manifest`、接收状态和处理状态，核对现有表与接口，避免重复建模。
5. 提交契约、用例、后续迁移草案和第 2 周任务清单。此工作包不向源库写入，不修改已执行迁移。

允许写入范围为仓库文档、合成测试夹具、接入预检辅助代码及本地测试输出；敏感配置保持 Git 忽略。后续接入实现再按对应工作包扩大写入范围。

**WP-01 退出条件：**连接状态有实测结论，首表可用性和缺失信息明确，三类入口能用同一批次及资产契约表达，并有可以自动对照的输入输出样例。

本轮交付的是方案和调研；测试库尚未连接，以上功能尚未因本方案而实现。现有代码验证与公开产品证据见[完整报告](30-warehouse-product-feasibility.md#12-验证记录研究限制与证据)。
