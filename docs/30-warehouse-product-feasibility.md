# 九章数据仓库产品分析与可行性报告

当前执行以[整库与每日入湖方案](31-warehouse-implementation-plan.md)为准：先接入整个测试库并持续接收每天的数据，再扩展 API、模型及治理；取消工时与按周排期。

2026-09-16 用户确认本报告的一期产品目标全部纳入开发验收，页面先用简单实现接通真实操作，后续再框架化。本报告中的基线与调研数据保留原时点；最新实现复核和完成情况见 [35 号记录](35-lake-review-and-remediation.md)。原实现存在关键缺陷及未开发能力，不能据旧测试数量判断完整产品已经完成。

## 结论摘要

**建议把九章定位为“面向小型数据团队的通用数据仓库建设与运营平台”：统一数据库、REST API 和文件夹入湖，支持仓库建模、质量检查、版本发布与授权使用。** DevOps、销售、工单等都是主题域实例，产品导航、核心模型和验收口径应保持通用。

推荐沿用现有 Java 控制面、Worker 与 PostgreSQL 基础，由 AI 连续完成可验证的实现切片。首个交付是“整个指定库首次入湖 + 每日持续运行 + 失败恢复”，完成后再扩展“入湖资产 → 标准模型 → 发布数据集”。接入基础不等待业务指标和全套页面完成。

- **第一优先级是整库持续入湖**：默认覆盖指定库全部基础表、关联表、字典表和空表，记录明确的未支持对象；每日运行、漏跑发现、幂等、原件留存、版本和恢复属于首版基础能力。
- **每日文件采用同一基础契约**：区分到齐、未交、合法空数据、迟到、更正与重复；结构化格式包括 CSV、Excel、JSON/JSONL、Parquet。外部负责落目录，九章不绑定具体传输工具。API 继续作为后续接入目标。
- **重点借鉴**：Dagster 的资产视角、SQLMesh 的变更计划、NiFi 的文件发现与处理分离、dlt 的声明式 API 接入、OpenMetadata 的资产详情组织。借鉴产品方法不等于同时部署这些产品。
- **本轮实时核验 18 个 GitHub 仓库**。既看关注度，也看默认分支近 30 天提交与 Release；不按 Stars 排名直接选型。DataSphereStudio、Taier、Dinky 的产品界面和流程有参考价值，但本次窗口内默认分支均未发现提交，不作为“近期高活跃”样本。
- **可行性按实际运行结果判断**：先通过全表覆盖、类型保真、连续批次、重复执行、断点恢复和缺失识别验收。当前没有源库规模和负载实测，不能承诺任何规模都可每日全量；逐表证明增量能力后再优化。

本报告是产品方案与研究结果，不直接改写已批准的业务规则或技术准入记录。代码基线为 `a5ae506`；调研日期为 2026-09-15。用户已提供测试源。严格 TLS 曾因证书信任失败停止；用户随后授权该测试源例外，已通过加密只读连接发现 157 张基础表并生成首批计划，随后完成一次真实原始快照和一个每日窗口；敏感连接配置不进入报告。详细运行证据见 34 号记录。

## 1. 产品定位：建设和运营数据仓库

### 1.1 目标用户与工作

| 角色 | 在九章完成的工作 | 应获得的结果 |
|---|---|---|
| 数据开发人员 | 登记来源、映射字段、维护 SQL 模型、测试和发布 | 一份可复用、可重算的数据资产 |
| 数据负责人 | 确认粒度、口径、负责人、质量规则和变更影响 | 知道数据是否可用、为什么可信 |
| 分析师、报表开发人员 | 查找数据集、查看字段与示例、申请访问、连接查询 | 找得到、看得懂、用得稳 |
| 平台管理员、运维人员 | 配置执行资源、查看失败、补数、备份和恢复 | 故障可定位，恢复有路径 |

一期可由同一人兼任多个角色，权限动作仍要区分。产品的首要用户是数据建设和使用人员；业务主题负责人提供规则及验收样本。

### 1.2 产品承诺

“将异构来源变成有结构、有历史、有质量、有负责人、可授权复用的数据集，并让其持续更新。”

这包含真正的数据仓库工作：确定事实表粒度、维度与业务键，处理跨来源标识、历史变更、增量与修订，建立可共享的明细和汇总模型。日报、月报只是这些模型的一种消费形式；API、分析工具及文件导出也可以消费数据集。

一期使用成熟存储和计算引擎承载数据。九章维护使用这些引擎的产品契约与流程，不开发新的 SQL 优化器、分布式存储引擎或事务协议。

### 1.3 三个容易混淆的边界

| 对象 | 产品含义 | 一期落点 |
|---|---|---|
| 文件交付目录 | 外部传输工具放文件的地方，文件可能还在变化 | 只读扫描，不能直接视为可信湖数据 |
| 原始湖区 | 平台接收、校验并登记的不可变原文件、API 响应与抽取片段 | 文件/对象持久区 + 入湖清单 + 元数据 |
| 数仓模型与数据集 | 从受控输入构建的标准明细、维度、汇总及对外契约 | PostgreSQL 起步，按需求演进分析引擎或湖表 |

**将文件复制进一个目录不代表完成数据湖治理；建立一个 PostgreSQL JSON 表也不代表已经完成数据仓库产品。** 数据发现、结构、版本、来源、质量、权限和生命周期必须随数据一起管理。

## 2. 核心产品对象与使用流程

### 2.1 围绕数据资产组织产品

建议稳定下来的一组产品对象：

| 对象 | 用户需要理解的含义 | 必须保留的信息 |
|---|---|---|
| 项目/空间 | 一个协作与权限范围 | 成员、环境、资源边界 |
| 主题域 | 一组相关业务概念 | 负责人、业务键、共享维度 |
| 来源与来源对象 | 某数据库表、API 资源、目录文件集 | 连接引用、Schema、增量能力与限制 |
| 入湖资产版本 | 一批已经接收的原始数据 | 文件/对象清单、哈希、来源时间、入湖时间、批次 |
| 数据模型版本 | 如何把输入变成某张明细/维度/汇总表 | 粒度、键、SQL、依赖、测试、历史策略 |
| 运行实例 | 某一版本在某个窗口的实际执行 | 输入版本、进度、失败原因、重试和产出 |
| 数据集契约/发布 | 允许下游使用哪些字段和哪个完整结果 | 字段语义、授权、截止时间、质量、release |

第一版不追求实体数量。先把稳定 ID、对象关系、状态与 API 明确，避免同一个概念在调度器、接入器和控制台各有一套名称。

### 2.2 三条主流程

**建设数据**：创建项目 → 选择来源 → 预览和确认结构 → 配置入湖规则 → 接收首批 → 建立模型 → 检查结果 → 发布数据集。

**使用数据**：搜索数据集 → 查看业务说明、字段、粒度、质量与更新时间 → 获得授权 → 获取 SQL 连接示例或受控 API → 查询固定发布版本。

**处理变化**：发现迟到、文件修订或模型变更 → 查看影响的数据集和时间范围 → 生成重算计划 → 在隔离结果上验证 → 发布新版本 → 保留旧发布和修订原因。

### 2.3 最小控制台信息架构

1. **工作台**：待处理异常、过期数据集、最近发布、当前项目。
2. **数据接入**：数据库/API/目录来源、结构预览、规则、批次与错误。
3. **数据开发**：主题、模型目录、版本差异、依赖和开发区样例结果。
4. **运行运维**：任务实例、日志摘要、重试、取消、补数与资源排队。
5. **数据资产**：已登记/已发布资产、字段、质量、来源、负责人、授权说明。
6. **发布与管理**：待发布变更、历史发布、项目角色和环境配置。

不按 SeaTunnel、dbt、DolphinScheduler 的组件名称分菜单。开发、运维和消费视图共享同一个资产 ID。第一条链路就要有最小页面，不应一直等全部后端完成才验证用户能否操作。

## 3. 接入优先级与统一基础

| 来源 | 实现顺序与交付 | 每次运行都必须具备 |
|---|---|---|
| 数据库 | 最先完成指定 MySQL 库全部基础表首次全量，随后每日快照；逐表验证增量或 CDC | 固定清单、表覆盖、空表记录、实际读取边界、持久化清单、失败恢复 |
| 文件夹 | 紧随数据库接入；目录发现及四类解析逐项完成，交付日历与账本从首版共用 | 交付完整性、缺失/空交付区分、迟到/更正、重复识别、原件与解析状态分离 |
| REST API | 在同一原始层和批次基础上扩展主动拉取 | 分页、认证引用、限流、接收检查点、原响应留存、业务成功判定 |

三类来源统一记录 `asset_version + batch + source_position + manifest + schema_version + ingestion_state`，接收、解析、加工和发布状态独立。指标质量门禁不能成为保存原件的前置业务条件；传输完整性和原件可重放则是入湖基础条件。

API 推送在出现真实场景时增加签名、事件幂等键、限额和异步接收；不影响当前整库主线。首次整库、每日数据库策略、系统清单、一致性范围及断点恢复细则见[实施方案第 4–5 节](31-warehouse-implementation-plan.md#4-首次整库如何保证覆盖与保真)。

## 4. 文件夹入湖的详细规划

### 4.1 产品配置

管理员配置目录根、包含/排除模式、递归深度、扫描周期、稳定等待策略、最大文件大小、最大积压量和所属项目。数据开发人员配置格式、字段、主键、业务日期、追加/更新/完整快照语义以及异常处理规则。上述限额需要用实际文件验证后确定，不在本报告宣称容量已满足。

外部可以人工复制、定时传输或通过现成工具落文件。Worker 只看到一个配置目录；网络盘由部署层挂载，连接凭证和重连属于挂载/运维边界。

### 4.2 处理过程

```text
外部把文件放入 inbox
  → 周期扫描并登记发现记录
  → 等待文件稳定 / 检查完成标志
  → 复制到平台 staging 并校验
  → 封存不可变原文件与入湖清单
  → 按已批准 Schema 解析
  → 检查与隔离异常
  → 形成标准数据版本
  → 模型构建、质量门禁、发布
```

优先使用轮询与持久化扫描状态，文件事件通知可作为加速信号。共享目录和进程重启后仍须可补扫，不能只依赖一次文件创建事件。

若外部可以配合，采用临时后缀写入后在同一文件系统原子改名，或提供完成清单。若无法配合，使用大小/修改时间跨多次扫描稳定、等待期、复制前后复核和解析检查；这些是启发式判断，不能证明生产方永远不会继续追加。需要强完整性的来源必须约定完成标志，或仅接收人工确认的候选文件。

### 4.3 身份、去重与修订

- 路径、文件名、修改时间都不是可靠的唯一业务键。同名内容变化应产生新版本，不能覆盖旧原件。
- 同一来源/逻辑文件版本的相同内容重放不重复入账；哈希只标识内容，不能决定两个业务批次是否语义相同。跨来源、跨周期不能全局静默去重。
- 文件内按业务键追加、更新还是替换某一分区，由来源契约决定；“重复文件”与“重复业务行”是两层校验。
- 封存清单记录逻辑来源、内容哈希、字节数、格式、Schema 版本、相对路径、发现/接收时间、业务时间范围、批次与解析结果。
- 原文件缺失、被外部改写、目录断连或复制中断，要有独立状态。错误记录与受控副本可留在平台隔离区，不自动挪走用户原文件。

### 4.4 四类文件的最小契约

| 格式 | 一期配置/验证重点 | 不能静默处理的情况 |
|---|---|---|
| CSV | 编码、分隔符、引号、表头、空值标记、日期和小数格式；支持流式读取 | 乱码、列错位、前导零丢失、日期自动猜错 |
| Excel | `.xlsx` 为基线；工作表、表头行、数据区、日期格式；公式采用可验证的缓存值或拒绝 | 宏不执行；合并单元格、无缓存公式、加密文件、旧 `.xls` 应明确支持状态或转换要求 |
| JSON/JSONL | 记录路径、对象/数组结构、字段映射、嵌套展开策略；大文件按记录流式读取 | 自动展开数组导致行数倍增、跨文件类型漂移 |
| Parquet | Schema、Decimal 精度、时间戳时区、逻辑类型、分区字段、压缩兼容性 | 精度截断、同字段异型、按文件名猜业务时区 |

Excel 已在一期范围；这里选择 `.xlsx` 是实施建议，若实际样例包含 `.xls`，须在格式准入时补充解析库和测试。未知字段可先提示差异，字段删除、类型改变、业务键改变进入阻断/审核流程。

### 4.5 验收样例

至少覆盖：边写边扫、写到一半中断、重复复制、同名更正、改名重复、迟到文件、空文件、坏文件、混合编码、Excel 多 Sheet/公式/日期、JSON 嵌套、Parquet Decimal/时区、Worker 重启、目录断连、多 Worker 竞争、超限文件及规则修订后重处理。

该规划借鉴 NiFi 的文件发现、文件年龄/大小及时间精度配置，具体的平台封存、版本和业务去重策略是本报告建议。[NiFi ListFile 官方说明](https://nifi.apache.org/components/org.apache.nifi.processors.standard.ListFile/)

### 4.6 每日文件交付完整性

来源可配置预期交付窗口、文件数或完成清单。没有文件时，有交付约定才标记缺失/超时；合法空数据需要空文件或明确空交付标志。多文件批次必须闭合后才记到齐。迟到文件归属原业务日期并记录实际接收时间，同名更正保留新旧版本；持续追加文件需明确封闭或轮转契约。

文件发现账本与每日数据库运行共用预期窗口、attempt/revision、租约和遗漏识别。原件保存与格式解析分别记状态，解析失败可重读原件；已成功接收不能被描述成所有格式都已可查询。完整规则见[每日文件入湖契约](31-warehouse-implementation-plan.md#6-每日文件入湖与数据库共用账本)。

## 5. API 入湖的详细规划

### 5.1 用声明式资源配置覆盖常见接口

来源配置包括固定服务地址、允许的目标、认证引用、资源路径、方法、字段路径、分页类型、游标字段、时间范围、每页大小、最大页数、超时、速率与重试上限。优先支持 page/size、offset/limit、返回 next-token/next-link 三类模板；接口声明不具备的增量或删除能力必须显示出来。

连接测试应同时检查认证、结构、分页和上界行为。HTTP 200 仍可能是业务错误或空响应，成功判定需要来源专属的响应契约。任意 URL、任意 header 凭证或任意 SQL/shell 不应成为普通用户的执行入口。

### 5.2 原响应与标准记录分开留存

每页/片段保留原响应体和脱敏请求说明，凭证、Cookie 和认证头不入湖。记录请求窗口、分页位置、响应时间、状态、记录数及摘要；空窗口也生成可核验清单。

遇到 429/临时错误按来源策略退避；永久认证失败停止并提示。断点重试可能重读数据，下游按明确业务键幂等处理。来源无法提供稳定分页或快照时，应暴露一致性限制，并安排重叠回读或对账；不宣称“恰好一次”。

API 成功接收原始片段只推进接收检查点；标准化与模型的处理进度独立记录。解析失败时保留原始输入，以便改规则后重算，不必强迫重新请求所有 API 页面。

dlt 的 REST source 以声明方式描述资源、分页、认证和增量，适合做限时接入适配实验；九章仍需控制 Schema 晋级、凭证边界和检查点提交。[dlt REST API 官方说明](https://dlthub.com/docs/dlt-ecosystem/verified-sources/rest_api/basic)

### 6.2 与九章最相近的一站式产品

**DataSphereStudio：借鉴工作空间和工具整合契约。** 其 AppConn 将 SSO、组织关系和开发流程作为整合层，体现统一产品并非仅把多个工具链接放在一起。当前 README 也有规划中/旧兼容矩阵内容，不能把整张功能清单当成当前可直接使用的能力。九章可采用“统一项目、统一运行 ID、统一错误和发布”的思路；对两人团队，整套 fork 和持续同步其生态的成本偏高。[DSS 仓库](https://github.com/WeBankFinTech/DataSphereStudio)

**Taier：借鉴开发、发布、运维的分工。** 项目包含 IDE、任务依赖、版本、参数和多引擎任务，适合参考数据开发工作台。但其设计覆盖 Hadoop/Flink/Spark 等环境，当前九章是否需要这些设施没有证据。近期发布仍存在，因此不能因近 30 天无主分支提交就断言失去维护。[Taier 仓库](https://github.com/DTStack/Taier)

**Dinky：实时 SQL 工作台参考。** 核心围绕 Flink 实时开发与作业运维；用户尚未提出实时处理时效目标，一期不应为贴近其功能清单增加 Flink。[Dinky 仓库](https://github.com/DataLinkDC/dinky)

**Apache Hop：可视化 ETL 的成熟参考。** 具有管道、工作流和图形开发工具，可在非 SQL 人员需要大量转换算子时单独评估。当前两人团队更适合 SQL 与规则配置，全面自研拖拽画布会明显增加工作量。GitHub 观测标签含 `rc1`，即使 API 的 prerelease 字段为 false，也应复核正式发行渠道。[Apache Hop 仓库](https://github.com/apache/hop)

### 6.3 活跃产品中值得直接借鉴的模式

| 产品 | 公开资料体现的做法 | 九章应怎样采用 |

| Dagster | 用资产定义连接持久结果、生产逻辑和依赖；支持按资产组织开发与运行 | 从数据集详情追到输入、模型、质量和运行；首页不只有任务成功数 |

### 6.4 组件适配与本轮重要变化

- **SeaTunnel / DolphinScheduler**：近期有默认分支更新，仍适合作为既有接入与编排路线的候选。平台要通过适配器关联运行与资产，不读取或改写它们内部元数据库。[SeaTunnel](https://github.com/apache/seatunnel)、[DolphinScheduler](https://github.com/apache/dolphinscheduler)
- **dbt**：旧 `dbt-labs/dbt-core` 地址已重定向到 `dbt-labs/dbt`。本轮观测到 v2.0.1，但固定提交 README 仍将 v2 标为 beta，并说明主分支改为 Rust、v1 在 `1.latest` 分支；仓库源码许可与带定制的发行物许可还须区分。现有 dbt Core 1.12.4/dbt-postgres 1.11.0 PoC 应保持独立基线，不能直接升级替换。[固定提交 README](https://github.com/dbt-labs/dbt/blob/ba280b8e69e9b6a699f3071a405bd10aa9ab248b/README.md)
- **Airbyte**：连接器和接入配置体验可参考；根 LICENSE 本轮读取为 ELv2，GitHub `NOASSERTION` 不能解释成没有限制或宽松许可。按现有治理规则，不进入默认交付组合。[根许可证](https://github.com/airbytehq/airbyte/blob/7c9cd920687bde761193a56da8ad91e2067e5aad/LICENSE)
- **Doris**：属于分析数据库，可在实际扫描、并发和成本数据表明 PostgreSQL 不足时验证；拥有分析引擎并不自动获得接入、模型开发和资产运营能力。[Doris](https://github.com/apache/doris)
- **Iceberg / Lakekeeper**：Iceberg 是开放湖表格式，Lakekeeper 是 REST Catalog；两者均不是完整数仓产品。需要多引擎访问、湖表快照、Schema/分区演进时再评估，不因为“入湖”一词就提前引入整套实时湖仓。[Iceberg 官方说明](https://iceberg.apache.org/docs/latest/)、[Lakekeeper](https://github.com/lakekeeper/lakekeeper)

## 7. 产品方案选择与推荐架构

### 7.1 四种建设路线

| 路线 | 适用场景 | 对当前两人团队的判断 |
|---|---|---|
| 直接使用成熟工具组合 | 主要目标是内部用数，可接受多个工具界面 | 最快建立数据能力；先确认是否真的需要统一九章产品 |
| Fork 一站式平台 | 与原平台功能和部署生态高度一致，有持续维护人员 | 当前不优先；原平台组件多、升级和定制耦合成本难压缩 |
| 自研产品流程 + 复用执行组件 | 要统一用户体验、数据契约和交付方式，并保留可替换执行层 | **推荐**，与现有代码投入相容 |
| 从头自研全部引擎 | 有长期研发和运维团队，目标是基础设施产品 | 超出一期能力和资源范围 |

推荐路线的成立条件是：统一资产、权限、版本发布和实施体验确实有用户价值。若调研后发现只有开发人员自己用 SQL，每月少量任务，成熟工具加约定式配置可能已经足够；应避免为了自有界面承担持续产品成本。

### 7.2 推荐的职责分工

```text
九章控制台 / 控制 API
  项目与角色 · 来源契约 · 模型版本 · 资产目录 · 质量门禁 · 发布记录
                     │ 受控任务与稳定运行 ID
                     ▼
接入 Worker ── 数据库 / REST API / 文件夹读取适配器
                     │
                     ▼
平台原始湖区 ── 不可变原件、原响应、抽取片段、Schema 与 manifest
                     │
                     ▼
标准明细与维度 ── SQL 模型构建 ── 公共汇总 ── 数据集候选版本
                     │ 质量通过、授权校验、原子切换
                     ▼
已发布数据集 ── SQL 授权视图 / 后续 API / 文件导出

调度组件负责执行依赖；平台负责“哪个版本可以给谁使用”。
```

### 7.3 第一版保持简单，但保留演进路径

- 控制面沿用 Java/Spring Boot；PostgreSQL 保存元数据。现有批次、租约和权限机制可以复用，仍需真实故障场景验证。
- 原始湖区先实现一个持久化文件存储后端及清单协议，路径由平台管理。外部 inbox 与湖区逻辑分离；后续可增加既有、经批准的 S3 兼容存储后端。不要默认新部署某个对象存储产品。
- 标准化明细、维度和对外服务先放 PostgreSQL；原件与处理模型可独立重放。暂不将“文件区 + PostgreSQL”称为已具备 Iceberg 式多引擎 ACID 湖仓。
- 数据库接入优先复核既有 SeaTunnel PoC；API 接入对比现有 Worker 轻量读取器与 dlt 库适配。只在实际样例、状态恢复和维护成本证明更好时采用 dlt，不默认新增一个常驻平台。
- 文件夹扫描、幂等登记、租约与版本由九章管理。解析器采用固定版本、许可明确的库；Excel 不能因为某工具支持“文件”就默认已覆盖。
- 先沿用 DolphinScheduler 和已锁定的 dbt v1 组合做正式化验证；不同时增加 Dagster、Kestra、NiFi、Hop。SQLMesh 作为变更/隔离方案备选，是否替换须有对比实验和迁移成本记录。
- Iceberg Catalog、分布式查询、完整治理套件分别按多引擎、容量、多团队发现需求触发。接入到原始湖区的成功与对外数据发布的成功是独立状态。

| 能力 | 基线实际状态 | 下一步交付 | 优先级 |

## 9. 可行性与运行成本

### 9.1 以真实接入结果判断

| 维度 | 当前判断 | 验证方式 |
|---|---|---|
| 交付效率 | 收敛主线可提高执行效率 | 整库接入优先，复用现有骨架，AI 连续完成实现、验证和修复；不并列建设多套工具 |
| 数据正确性 | 整库原始快照已实测，长期恢复仍待演练 | 全表覆盖、空表、类型保真、快照范围和失败恢复分别验收 |
| 每日持续运行 | 必须与首次全量一起实现 | 连续窗口、重复触发、停机恢复、缺失识别、补采与实际时点记录 |
| 性能与容量 | 尚无真实全库画像 | 实测读取量、源库负载、传输速度、落盘容量和积压，逐表决定全量/增量 |
| 文件交付 | 目录入口明确，真实交付规则待接入时落实 | 四格式样例、完成信号、缺失和空数据、迟到与修订验收 |
| 商业和许可 | 不从 GitHub 活跃度推导市场价值或交付许可 | 客户与运行成本另有证据；固定组件、驱动、解析器及镜像逐项准入 |

### 9.2 观察资源与完成结果

取消人周、人日、利用率和按周排期；旧的人员排期不作为当前执行依据。效率由完成的可运行能力衡量，基础正确性和恢复能力不能靠省略验证换取。

记录每日抽取字节/行数、单表峰值、单文件大小、实际读取时段、API 请求量、对象数量、保留版本和备份量。依此选择全量、增量、压缩、生命周期与存储后端；不填未经测量的吞吐或费用。

产品完成指标包括：指定库表覆盖率、完整批次覆盖的应有窗口、重复提交数、失败恢复结果、原件可重放率及缺失告警可见性。数据集质量和商业价值是后续阶段的独立评价。

| 顺序 | 可验收结果 | 下一步 |
|---|---|---|
| 全库发现 | 指定库全部基础表、Schema、类型及接入策略有清单 | 执行首次整库抽取 |
| 首次整库入湖 | 所有必需表和空表均有可校验原始资产、系统清单与一致性标记 | 持续运行并处理失败 |
| 每日数据库入湖 | 运行日历、去重、补跑、缺失、历史版本与结构变化均有记录 | 完善文件每日交付 |
| 每日文件入湖 | 目录、交付完整性、四格式解析及更正/迟到均可验证 | 扩展 API 及加工 |
| 完整数仓目标 | API、模型、质量、授权数据集与第二主题复用 | 按实际容量扩展引擎及治理 |

执行明细及验收以[整库与每日入湖方案](31-warehouse-implementation-plan.md)为准。首个系统入湖完成必须包含每日持续运行，不以单次导出或单表演示代替。业务建模与复杂页面不阻塞原始接收；来源范围、Schema、完整性和访问控制随接入一起完成。

## 11. 主要风险与止损条件

| 风险 | 应对与明确停止条件 |
|---|---|
| 范围膨胀 | 新来源/格式/实时场景按主线依赖排序；一期不同时承诺任意接口、在线 IDE、拖拽 ETL 和完整治理平台 |
| 文件仍在写入 | 有完成清单优先；无握手的稳定检查只能提供有限保证；高完整性场景无交付协议则停止自动发布 |
| API 分页不稳定 | 固定窗口、回读、来源键对账；无法证明覆盖范围则标为不完整，不推进正式发布 |
| 自动推断结构导致错数 | 推断仅做建议；破坏性变化阻断；保留原件与解析规则版本 |
| 检查点与处理状态混在一起 | 原始接收、标准化、模型发布各有进度；失败后可从封存输入继续 |
| 多组件重复管理状态 | 平台管资产与发布事实，执行组件管任务过程；同一职责只选一个主要实现 |
| 存储切换被低估 | 文件区、对象存储和 Iceberg 的提交/权限语义不同；新后端必须通过相同故障与恢复测试 |
| 权限只有页面判断 | Worker、控制面、数据消费使用不同身份；数据查询入口验证行/列范围，原件按敏感级别授权 |
| 两人持续运维超负荷 | 先单部署单元、受控来源与清晰限额；若维护成本超过约定预算，缩减功能或采用现成产品 |
| 组件许可/发行版变化 | 固定发行物复核；dbt v1/v2、企业功能、解析器/驱动分别准入；不按根 LICENSE 一次性放行 |

最关键的验证门槛：**第二个业务主题能通过新增来源配置、领域模型、SQL 和授权完成建设，平台核心不需要加入它的业务状态或专属接口。** 若做不到，应先修复抽象边界，再继续扩张。
