## 2. 真实联调前的最小资料包

资料不足不阻止合成实验设计；不索取真实密码、Token、完整个人信息或生产数据库备份。

### A. 产品与对象说明

- DevOps平台名称、版本/自研情况、可协调的接口负责人。
- 项目、团队、需求对象说明及字段字典；先不要求提交代码、流水线或全部缺陷数据。
- 主键是否跨项目唯一；项目/需求与团队是单归属还是多对多；ID改变、合并或迁移规则。
- 状态字典：名称、代码、终态含义、允许的流转以及取消/删除如何表示。

### B. 接入方式（三选一或组合）

| 可提供方式 | 最小资料 | 验证边界 |
|---|---|---|
| API | 脱敏文档/OpenAPI、请求/响应样例、分页/排序/增量过滤、认证方式说明、限流/错误码、时间字段与时区 | 不要交付真实Token；测试地址与凭证通过约定安全渠道配置 |
| 只读数据库 | 表/视图结构、字段说明、主外键/索引、可读范围、更新时间/软删除字段、历史表说明、允许查询窗口 | 不需要生产写权限；确认厂商允许读取，不依赖未授权内部表 |
| 文件导出 | CSV/JSON等小样本及字段说明、导出截止时间、是否含历史 | 可验证加工；不能代替真实API分页、认证和增量联调 |

### C. 脱敏样例

建议20–50条需求当前态，配套若干完整状态/归属变更轨迹；数量是资料建议不是硬性门槛。包含正常完成、未完成、重开、取消/删除、跨月、迟到录入、团队变更和缺失字段等案例。保留各文件间一致的匿名ID和相对时间关系。

期望字段示例（仅映射需求，不宣称源平台必有）：

- 需求：需求ID、项目ID、标题脱敏或省略、当前状态、创建/更新时间、首次开始/完成时间（如有）、取消/删除信息。
- 状态事件：事件ID或稳定去重键、需求ID、旧状态、新状态、业务生效时间、记录时间或可用顺序号。
- 归属：需求/项目/人员ID、团队ID、关系类型、有效起止时间、变更记录时间；多团队关系还需主责/协作及权重规则。
- 团队：团队ID、匿名名称、上级组织（如适用）、有效起止时间。

只提供现有字段，不要求业务系统先改造。每项缺失明确影响，后续决定补采还是缩小指标范围。

## 3. “状态历史”和“团队历史”是什么意思

### 状态历史

指需求、任务等业务对象在不同时间的生命周期状态，不是服务器或容器运行状态。例如一条合成需求：

| 时间（上海） | 变化 |
|---|---|
| 2026-08-28 09:00 | 创建，待处理 |
| 2026-08-29 10:00 | 开始处理 |
| 2026-08-31 16:00 | 完成 |
| 2026-09-02 11:00 | 重新打开 |
| 2026-09-04 15:00 | 再次完成 |

只有当前“完成”状态，无法从中判断2026-09-02日末是否仍未完成，也无法区分第一次和第二次完成。创建/首次完成等可信字段可以支持部分流量与耗时指标，但不能冒充完整历史。

### 团队历史

主要区分三种关系：需求/项目由哪个团队负责、人员属于哪个团队、团队本身的改名/合并/组织层级变化。示例：某需求2026-08-31前由A团队负责，2026-09-01转给B团队。必须决定8月数据归A还是按当前组织重述给B，不能无意将全部历史改写。

建议历史绩效按业务发生时归属；当前组织视角若需要，作为单独命名的重述视图。不同指标可采用创建时、开始时、完成时或期末归属，但必须逐项签字。人员归属不能未经确认等同于需求归属；历史统计归属也不等同于当前访问权限。

## 4. 合成实验的三类指标建议（不替代正式口径）

| 类别 | 合成实验候选 | 必须显式定义的规则 |
|---|---|---|
| 流量计数 | 周期内新建需求数 | 根据创建时间筛选，按来源+需求ID去重；统计范围、取消/删除的影响以及归属规则单独声明 |
| 周期耗时 | 周期内首次完成需求的平均处理时长 | 候选为首次开始处理至首次完成的自然小时，保留总时长/有效样本数；缺失或负时长隔离，不填零；重开第二次完成不混入“首次完成”样本 |
| 期末存量 | 日末/月末未完成需求数 | 使用周期结束边界之前的历史状态；已取消/删除、未创建对象和未知状态如何处理必须在实验fixture规则中明确 |

以上只是建议的样例契约，实施时先形成可复核的fixture规则与黄金结果；用户验收真实口径前不用于生产报表。月均从符合月度样本口径的明细重算，不平均每日均值；月末存量不是每日存量相加。一个对象的后续变化可能使后续多日期末存量都受影响，不能只重算变化当天。

## 5. 日报发布规则

实施方确定T+1 06:00（Asia/Shanghai）为目标。例如2026-09-10 06:00前发布2026-09-09的日报，业务事件范围为[2026-09-09 00:00, 2026-09-10 00:00)。

- 上游实际可用时点及批处理耗时决定任务启动时刻，源资料未到位前不承诺固定02:00启动等时间。
- 06:00前必须完成接入、转换、质量检查、发布；上游迟到或检查失败时保留上一成功发布，展示数据业务截止时间、生成时间和延迟状态，不以“准点”牺牲完整性。
- 增量以来源检查点读取新变化；重算按受影响的业务日期及依赖传播，不只按摄取日期处理。可选回看窗口只是兜底，不替代事件追踪或对账。
- 日报与月报的发布指针可独立；冻结月份的更正先进入候选版本，不能因为每日重算而静默覆盖正式月报。

## 6. 月报更正的含义与可选项

业务事件发生时间与系统收到/修正时间可能不同。例：2026-08-31完成的需求到2026-09-03才补录，如果8月报表已生成，是否以及如何更正8月结果就是月报更正规则。

| 方案 | 行为 | 好处 | 代价/适用条件 |
|---|---|---|---|
| A 始终滚动更新 | 发现迟到/纠错后自动构建并发布新月度版本，保留旧版本 | 最新数据持续纠正，流程简单 | 过去月份数字会变化，已导出报表需标明版本；适合日常分析 |
| B 结账前滚动，结账后审批修订（推荐） | 先发布暂定版；结账后正式版固定，更正需说明差异、审批后发布修订版 | 同时支持纠错、审计和已发布数字的稳定性 | 需要结账、审批和版本查询；适合管理统计、考核及私有化交付 |
| C 冻结后不改原月报 | 结账后原正式版保持不变，更正记录在单独调整数据集中 | 原发布始终固定 | 原月报不再反映最新事实；不建议作为唯一分析口径 |

若选择C，调整记录仍指向原业务月份，不直接把“8月完成数”算进9月完成数；如需调整列，另建有明确含义的数据集。

B的建议参数（待用户批准）：自然月；次月5日06:00结账；此前每日随日报更新上月暂定版；用户为PoC审批人。若源完整性/质量未通过，阻断结账并标记延迟，不自动标为正式。

例如2026年8月报表拟于2026-09-05 06:00结账。2026-09-07发现新增迟到数据后，生成差异和候选修订版；用户批准后发布修订版，原版保留。此处是规则示例，不代表本项目已经发生这些发布。

“正式版v1/修订版v2”是展示名称，底层每次构建仍对应独立不可变release_id；不与软件版本混用。冻结发布必须引用已物化且不可变的数据，不能用指向持续更新明细表的视图冒充冻结月报。

## 7. SQL直连供数的PoC调整

- PoC优先测试数据库连接、发布表/视图、只读角色和SQL查询，业务数据查询API推后；平台管理API仍可存在，不与报表供数API混淆。
- 报表账号只访问授权发布空间，不能读RAW、加工中间表或平台元数据库；写入和结构变更权限分离。
- 若无法传递报表用户身份，使用隔离账号/授权视图，或由可信报表平台承担已验证的权限责任；禁止声称共享数据库账号天然具备最终用户隔离。
- 单条SQL与一组报表SQL分别验证一致性：仪表盘多次查询、下钻必须固定release_id或使用经验证的同一事务快照，不能默认每次读取活动视图就构成整体一致。
- 迟到重算、质量失败、版本切换和冻结月报不得导致报表读到半更新数据。报表产品及连接池/事务行为是真实联调待办。

## 8. 百万级、300 QPS的验收解释

用户给定的是目标量级，不是已通过的容量。必须区分每秒查询数与同时连接/正在执行数，也不能把一张报表的刷新次数直接等同于SQL次数。

需进一步确认百万级是当前需求对象总数、事件表总数还是每日新增。一个对象可能产生多条状态/团队历史，测试需分别登记各层行数、宽度、历史跨度与数据倾斜。

建议压测基线（待确认）：将300 QPS视为数据库端实际完成的报表SELECT吞吐；覆盖汇总筛选、趋势及分页下钻。冻结SQL模板、比例、返回行数、权限范围及延迟门槛后测试。分别报告提交速率、成功吞吐、超时/错误、P50/P95/P99、冷/热缓存、连接数及CPU/内存/磁盘资源。

沿用06文档P95≤3秒作为候选而非已批准SLA；测试持续时长及峰值目标待冻结。正常服务与批处理/发布竞争场景分别测试；压测客户端尽量独立，记录网络位置及资源。若NAS不足，可完成机制验证，但性能项标记失败/未达标，不下调300 QPS目标冒充通过，也不未经用户同意换生产平台。
